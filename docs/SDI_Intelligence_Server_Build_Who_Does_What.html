SDI Intelligence server: who does what

Revised 5 October 2026 · Windows Server 2025 on the machine, the graphics card and SOLIDWORKS in a Windows 11 Pro VM, and a Linux VM beside it. A Windows 11 Pro host was considered and set aside: it cannot give a graphics card to a VM.

Jack builds the machine and hands over two virtual machines that behave like new computers on the network: a Windows 11 Pro one with the graphics card inside it, and a Linux one. James takes them from there, exactly as he would set up a laptop. The handover checks in the middle are the line between the two. The first section shows how the parts fit together, why the host is Windows Server, and what to watch for.

Scan 3XS · Threadripper PRO 9975WX (32 cores) · 128 GB ECC · NVIDIA RTX 4000 Ada SFF 20 GB · 2 × 2 TB NVMe · Windows Server 2025 host · VM 1 Windows 11 Pro: the card, SOLIDWORKS, Excel, runner 1 · VM 2 Linux: James's services · optional VM 3 Windows 11 Pro for a second runner

How it fits together

One machine, split into a host and two virtual machines. The graphics card and SOLIDWORKS live in the Windows VM; the Linux VM runs the services James names; the host runs the portal and the job queue and nothing that needs a desktop.

  1. Estimators start a job on the portal. It joins the queue on the host.
  2. The runner in VM 1, when it is free, takes the oldest job waiting. One job at a time. The Linux VM runs no estimates: it has no Excel and no SOLIDWORKS. A second Windows VM with its own runner can be added later (VM 3).
  3. SOLIDWORKS takes a licence from the pool on the host while it is open. The runner keeps it open, so VM 1 holds one seat all day.
  4. The runner reads and writes the job folders and books on the estimating shares, which stay on the file server.

Why the host is Windows Server and not Windows 11 Pro

Three things were asked of this machine: Remote Desktop into it, the graphics card in a VM, and SOLIDWORKS in a VM. Only a Server host gives all three.

What can and cannot be shared

The graphics card: one card, one VM.

Passed through (DDA), the RTX 4000 Ada belongs to VM 1 alone; the host and the Linux VM have none. It cannot be split between VMs: Windows Server 2025 only partitions a short list of data-centre cards (NVIDIA L4, L40S, A16 and similar) with NVIDIA's licensed vGPU driver, and this card is not one of them. Moving it to another VM needs both VMs shut down, so it is a maintenance job, not something that happens per request. The host does not need it. If the Linux VM ever needs a card of its own, a second card is fitted and passed to it the same way; DDA works for Linux guests.

The estimates: shared by the queue.

This is where "whoever is free takes the next one" happens. A second Windows VM with a runner means two estimates at once; each takes the oldest job waiting when it finishes the last.

SOLIDWORKS: the licences are shared, the program is not.

Each VM that uses SOLIDWORKS needs its own installation; it cannot run on the host and be reached from the VMs, and the engine drives it only on its own VM. A network (SolidNetWork) licence puts the seats in a pool on the host: SOLIDWORKS takes one when it opens and returns it when it closes, first come, first served, and designers' PCs can share the same pool. A standalone licence works in a VM but is tied to that VM's identity, so a rebuilt VM means a reactivation; the network licence avoids that.

The Linux VM: James's, with no desktop.

Ubuntu LTS server under Hyper-V, administered over SSH. It runs tooling, agents and any service that needs no Windows; the portal could move to it (it is a Python service and runs the same on Linux). Nothing that drives Excel or SOLIDWORKS goes here. Ubuntu carries the Hyper-V integration drivers in its kernel, so nothing extra is installed.

Test before buying another card.

The model extract may not need the graphics card at all: its geometry work runs on the processor, and SOLIDWORKS falls back to software graphics without a card. Run the extractor on job 12120 in a VM with no card and compare the result and the time with VM 1. If they match, a second Windows VM can run SOLIDWORKS without a card, and no GPU purchase is needed.

Gotchas

None of these stops the plan. Each one is a setting or a habit, and each is on a list below with an owner.

  1. The card is VM 1's, and touching it means stopping VM 1. A driver update inside the VM is an ordinary restart of the VM. Moving the card, or changing which VM has it, needs the VMs shut down. The host shows "Microsoft Basic Display" from then on; that is expected.
  2. One desktop in the Windows VM. VM 1 is Windows 11 and allows one interactive session. A Remote Desktop into it as a different user pushes the runner off and can stall an estimate. Rule: connect as the runner account (same session) and leave by handing the session back to the console with tscon, or use the Hyper-V console from the host, which shows the runner's desktop without logging it off. The host's own two admin sessions are the normal way in.
  3. Server drivers for a workstation board. Scan supplies Windows 11 drivers for the 3XS. Windows Server 2025 installs on the Threadripper PRO board, but chipset and network drivers may need to come from the board maker. Ask Scan to confirm before the build week.
  4. SOLIDWORKS version and licence. 2026 or later for Hyper-V 2025 support. A network licence is strongly preferred in a VM: a standalone one is tied to the VM's identity and reactivates on a rebuild.
  5. The VMs must be on the office network, not behind the host. Create an External virtual switch on the machine's network port so both VMs get fixed addresses and DNS names, and the portal, Remote Desktop and SSH reach them by name.
  6. Sleep and lock in VM 1. Windows 11 defaults: no sleep, no hibernate, no screen lock, no screensaver for the runner account, and an exemption from any domain lock policy. Auto-logon of a domain account needs Sysinternals Autologon with Windows Hello off for that account.
  7. Linux under Hyper-V. A Generation 2 Linux VM boots with Secure Boot only on the "Microsoft UEFI Certificate Authority" template; the Windows template refuses it. No desktop and no Enhanced Session: SSH.
  8. A host restart takes every VM down. Windows Update on the host is calmer than Windows 11 but a restart mid-run still loses that estimate. Host and VMs on different nights, and James told first.
  9. Licences add up. Server 2025 Standard per core (two 16-core packs for this processor) and client access licences; Windows 11 Pro and Office for VM 1 (and VM 3 if built); nothing for the Linux VM. Windows Server Standard's two free guest licences are for Windows Server guests, not Windows 11.
  10. Keep the estimating shares on the file server. Nothing here needs this machine to be a file server, and making it one puts the queue and the files on one restart.

Infrastructure: the host and the VMs

Everything below the applications: hardware, operating systems, network, accounts, backup. In build order.

The host (Windows Server 2025)

  1. BIOS: latest firmware; power on after AC loss; enable virtualisation (SVM) and IOMMU, which the GPU pass-through needs.
  2. Storage: set up the two NVMe drives (mirror or split OS / VMs — Jack's call) and install Windows Server 2025 with current drivers, from the board maker where Scan has none for Server.
  3. Network and domain: fixed IP, DNS name, join the domain.
  4. Hyper-V: add the Hyper-V role and create an External virtual switch on the machine's network port, so the VMs are on the office network.
  5. Service account for the SDI Intelligence portal service, with read/write to the estimating shares by UNC path (\\server\share, not K:).
  6. Firewall: allow the portal port (8071) from the office network and from the VMs.
  7. SOLIDWORKS licence manager (SolidNetWork): install it on the host with the reseller's serial, and open ports 25734 and 25735 to the VMs (and to designers' PCs if they share the pool). Windows Server is supported for the licence manager; it needs SOLIDWORKS 2025 SP3 or later on Server 2025, and must be at least as new as the SOLIDWORKS installs.

VM 1 (Windows 11 Pro): the graphics card, SOLIDWORKS and the runner

  1. Create it as Generation 2 with Secure Boot and a virtual TPM (Windows 11 requires both).
  2. Fixed resources: 12 virtual CPUs, 48 GB memory with Dynamic Memory off, a 300 GB+ virtual disk on NVMe.
  3. Pass the RTX 4000 through to the VM (Discrete Device Assignment), then install NVIDIA's RTX workstation driver inside the VM. GPU partitioning is not needed (and not available for this card). The host and the Linux VM then have no graphics card; that is expected.
  4. Windows 11 Pro, fixed IP and DNS name, joined to the domain, fully updated.
  5. Runner account: a dedicated domain user that logs on automatically at boot (Sysinternals Autologon, Windows Hello off for it); read/write to the estimating shares by UNC path.
  6. Power and lock policy: no sleep, no screen lock, no screensaver on the VM, exempt from any domain lock policy — SOLIDWORKS and Excel need a live desktop session.
  7. Admin access for James: Remote Desktop to the host (two admin sessions) and the Hyper-V console to the VM; the host's admin share (the laptop's push-to-server.ps1 copies through it); a tscon hand-back script on the runner's desktop.

VM 2 (Linux): James's services

  1. Create it as Generation 2 with Secure Boot on the Microsoft UEFI Certificate Authority template; no virtual TPM needed. 4 virtual CPUs, 16 GB memory, a 100 GB+ virtual disk. With VM 1 at 48 GB this leaves the host about 64 GB.
  2. Ubuntu LTS server, fixed IP and DNS name on the External switch, SSH open to James, an account for him with sudo. No graphics card unless a second card is fitted and passed to it.
  3. Both VMs start automatically with the host, VM 1 first.

VM 3 (Windows 11 Pro): a second runner, optional and later

  1. Same as VM 1 (Generation 2, Secure Boot, virtual TPM, Windows 11 Pro, fixed IP, domain, its own runner account with auto-logon, no sleep or lock), but no graphics card and no SOLIDWORKS; 8 virtual CPUs, 32 GB with Dynamic Memory off, 200 GB+ disk.
  2. Only after James's routing change (see his list), so jobs with SOLIDWORKS models always go to VM 1.

Running it

  1. Licences: Windows Server 2025 Standard per core (two 16-core packs for the 9975WX) and client access licences; a Windows 11 Pro licence and an Office licence for each Windows VM; nothing for the Linux VM. Server Standard's two guest licences cover Windows Server VMs only.
  2. Backups: host and VMs (Windows Server Backup or the company tool, with the VMs exported), one restore tested before go-live.
  3. Windows Update: restarts scheduled out of hours, host and VMs on different nights, James told first.
  4. Antivirus: apply the exclusions James supplies (SOLIDWORKS temp and the output folders).
  5. Power: on the UPS, and set to start again after a power cut, with the VMs starting automatically.

Handover checks

Jack confirms these, then the machines are James's:

  • In VM 1's Device Manager the graphics card shows as NVIDIA RTX 4000 Ada with the NVIDIA driver, not "Microsoft Basic Display".
  • After a full restart of the host, both VMs start by themselves; VM 1 logs in as the runner account with nobody touching it and is still unlocked an hour later.
  • Signed in as the runner account, VM 1 can open and save a file in the estimating folders by UNC path.
  • From VM 1 and from a desk, the host answers on port 8071 (once James's service is running, this is just a browser test).
  • From VM 1, the licence manager on the host answers on port 25734.
  • From James's laptop: Remote Desktop to the host as an administrator while another admin is already connected; the Hyper-V console shows VM 1's desktop; SSH into the Linux VM by name.

Applications: the laptop premise

Everything that makes it an SDI Intelligence machine, installed the same way as on the laptop.

On VM 1 (runs the estimates)

  1. SOLIDWORKS: install on VM 1 only and point it at the host's licence manager. Open one model to confirm the graphics card is in use.
  2. Office / Excel: install and activate; open one estimate book.
  3. PDM / Design Vault client, if models come from the vault.
  4. Python and Git, clone the repository, create the engine's .venv.
  5. The .env file, written by hand for this machine — never copied from the laptop.
  6. The runner: scheduled task at logon (restart-runner.ps1) pointing at the host's service.
  7. Hand Jack the antivirus exclusion paths.

On the host (runs the portal)

  1. Python and the service's own .venv, the backend files, and the host's own .env.
  2. Install and start the SDIIntelligence service; check the portal loads from a desk.

On the Linux VM

  1. What it runs is James's to name: tooling, agents, and any service that needs no Windows. If the portal moves here, the runners point at the Linux VM's name and it runs under systemd; it needs no access to the estimating shares, which only the runners read and write.

Proving it

  1. Run one known job (12645 or 12173) on VM 1 and compare the book and the run time with the laptop's.
  2. Restart the host and confirm the portal, both VMs and the runner all come back without anyone logging in.
  3. Remote in and out once through the Hyper-V console while a short job runs on VM 1, and confirm the job finished.
  4. The graphics test: run the SOLIDWORKS extractor on 12120 in a VM with no card and compare the extract and the time with VM 1. This decides whether a second card is ever needed.

Before VM 3

  1. Routing change in the engine: today whichever runner is free takes the next job, so a job with SOLIDWORKS models could land on VM 3 and be costed from the PDFs alone. Each runner will say whether it has SOLIDWORKS, and jobs with models will wait for one that does.

Agree together before the build week

Rule of thumb: if it would be the same on any Windows machine, it's Jack's. If it only exists because this is SDI Intelligence, it's James's.
