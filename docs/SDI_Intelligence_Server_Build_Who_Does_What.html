SDI Intelligence server: the build plan

Revised 5 October 2026 · The operating system installed on the machine is WINDOWS SERVER 2025. Windows 11 Pro exists only inside VM 1, the virtual machine that holds the graphics card and the tools people use. One Linux VM for Technical Design. No third VM.

Jack builds the machine and hands over two virtual machines that behave like new computers on the network: a Windows 11 Pro one with the graphics card inside it, and a Linux one. James takes them from there, exactly as he would set up a laptop. The first section says what runs where and why; then Jack's list, the handover checks, James's list, and the questions to settle together.

Scan 3XS · Threadripper PRO 9975WX (32 cores) · 128 GB ECC · NVIDIA RTX 4000 Ada SFF 20 GB · 2 × 2 TB NVMe · Windows Server 2025 host (Hyper-V, SOLIDWORKS licence manager) · VM 1 Windows 11 Pro: the card, estimating, client estimating, Client Briefing, Drawing Search · VM 2 Linux: Technical Design services

What runs where

The operating system on the metal is Windows Server 2025, and it runs nothing a person would use: Hyper-V and the licence manager. The Windows VM is the laptop, moved to the server, with the card: everything that needs a desktop, Excel, SOLIDWORKS or a SOLIDWORKS library. The Linux VM is Technical Design's: GitLab, PostgreSQL and the FastAPI services, which call the Windows VM over HTTPS for anything SOLIDWORKS.

  1. People reach every tool on VM 1 in a browser: the estimating portal, Client Briefing and Drawing Search each on its own port. The runner on the same VM takes the oldest job in the queue when it is free.
  2. SOLIDWORKS on VM 1 takes a licence from the pool on the host while it is open. The runner keeps it open, so VM 1 holds one seat all day.
  3. VM 1 reads and writes the job folders and books on the estimating shares, and reads W: for Drawing Search's index.
  4. The Linux VM reads W: for the Document Manager and holds the Design Vault on its own disk.

What can and cannot be shared

The graphics card: one card, one VM.

Passed through (DDA), the RTX 4000 Ada belongs to VM 1 alone; the host and the Linux VM have none. It cannot be split between VMs: Windows Server 2025 only partitions a short list of data-centre cards (NVIDIA L4, L40S, A16 and similar) with NVIDIA's licensed vGPU driver, and this card is not one of them. Moving it to the Linux VM is a shutdown of both VMs each way, so it is for an occasional overnight job, never a routine. If Technical Design ever needs a card of its own, a second card is fitted and passed to the Linux VM the same way; DDA works for Linux guests.

SOLIDWORKS: the licences are shared, the program is not.

SOLIDWORKS runs only on VM 1; the Linux VM reaches its four COM tools over the network. A network (SolidNetWork) licence puts the seats in a pool on the host: SOLIDWORKS takes one when it opens and returns it when it closes, first come, first served, and designers' PCs can share the same pool. A standalone licence works in a VM but is tied to that VM's identity, so a rebuilt VM means a reactivation; the network licence avoids that.

One runner, one estimate at a time.

With no third VM there is one runner, as on the laptop today. The queue still takes every job and prices them in order. A second runner is a later decision and would be a second Windows VM without a card.

The Linux VM is Technical Design's.

Ubuntu LTS server under Hyper-V, administered over SSH by the Technical Design team. It carries the FastAPI services, Production Design Extraction and the Design Vault, and nothing that drives Excel, SOLIDWORKS or a SOLIDWORKS library; those it reaches on VM 1 over HTTPS. Ubuntu carries the Hyper-V integration drivers in its kernel, so nothing extra is installed.

Gotchas

None of these stops the plan. Each one is a setting or a habit, and each is on a list below with an owner.

  1. The card is VM 1's, and touching it means stopping VM 1. A driver update inside the VM is an ordinary restart of the VM. Moving the card needs both VMs shut down. The host shows "Microsoft Basic Display" from then on; that is expected.
  2. One desktop in the Windows VM. VM 1 is Windows 11 and allows one interactive session. A Remote Desktop into it as a different user pushes the runner off and can stall an estimate. Rule: connect as the runner account (same session) and leave by handing the session back to the console with tscon, or use the Hyper-V console from the host, which shows the runner's desktop without logging it off. The host's own two admin sessions are the normal way in.
  3. Everything on VM 1 shares one restart. The runner, the portal, Client Briefing and Drawing Search go down together when VM 1 restarts, and a restart mid-run loses that estimate. Windows Update on VM 1 is scheduled out of hours and announced.
  4. Server drivers for a workstation board. Scan supplies Windows 11 drivers for the 3XS. Windows Server 2025 installs on the Threadripper PRO board, but chipset and network drivers may need to come from the board maker. Ask Scan to confirm before the build week.
  5. SOLIDWORKS version and licence. 2026 or later for Hyper-V 2025 support. A network licence is strongly preferred in a VM.
  6. The VMs must be on the office network, not behind the host. An External virtual switch on the machine's network port, so both VMs get fixed addresses and DNS names, and browsers, Remote Desktop and SSH reach them by name.
  7. Sleep and lock in VM 1. No sleep, no hibernate, no screen lock, no screensaver for the runner account, an exemption from any domain lock policy, and auto-logon with Sysinternals Autologon (Windows Hello off for that account).
  8. Linux under Hyper-V. A Generation 2 Linux VM boots with Secure Boot only on the "Microsoft UEFI Certificate Authority" template; the Windows template refuses it. No desktop: SSH.
  9. GitLab on the Linux VM wants ports 80/443 and git over SSH. Admin SSH and GitLab's SSH both want port 22; give GitLab its own port or its own address. PostgreSQL is opened only to VM 1 and the Linux VM itself, never to the office network.
  10. Licences add up. Server 2025 Standard per core (two 16-core packs for this processor) and client access licences; Windows 11 Pro and Office for VM 1; nothing for the Linux VM. Server Standard's two free guest licences are for Windows Server guests, not Windows 11.

Infrastructure: the host and the two VMs

Everything below the applications: hardware, operating systems, network, accounts, backup. In build order.

The host (Windows Server 2025)

  1. Confirm with Scan that Server 2025 drivers exist for the 3XS board, or where to get them.
  2. BIOS: latest firmware; power on after AC loss; enable virtualisation (SVM) and IOMMU, which the GPU pass-through needs.
  3. Storage: set up the two NVMe drives (mirror or split OS / VMs — Jack's call) and install Windows Server 2025 with current drivers.
  4. Network and domain: fixed IP, DNS name, join the domain.
  5. Hyper-V: add the Hyper-V role and create an External virtual switch on the machine's network port, so the VMs sit on the office network.
  6. SOLIDWORKS licence manager (SolidNetWork): install it on the host with the reseller's serial, and open ports 25734 and 25735 to VM 1 (and to designers' PCs if they share the pool). It needs SOLIDWORKS 2025 SP3 or later on Server 2025, and must be at least as new as the SOLIDWORKS install.
  7. Admin access for James: Remote Desktop to the host as an administrator (two sessions), and the host's admin share, which the laptop's push-to-server.ps1 copies through.

VM 1 (Windows 11 Pro, a virtual machine on the Server host): the graphics card and everything people use

  1. Create it as Generation 2 with Secure Boot and a virtual TPM (Windows 11 requires both).
  2. Fixed resources: 16 virtual CPUs, 64 GB memory with Dynamic Memory off, a 500 GB+ virtual disk on NVMe; automatic start with the host, automatic stop action "turn off" (DDA requires it).
  3. Pass the RTX 4000 through (Discrete Device Assignment): disable the card on the host, dismount it, assign it to the VM, then install NVIDIA's RTX workstation driver inside the VM. The host and the Linux VM then have no graphics card; that is expected.
  4. Windows 11 Pro, fixed IP and DNS name on the External switch, joined to the domain, fully updated.
  5. Runner account: a dedicated domain user that logs on automatically at boot (Sysinternals Autologon, Windows Hello off for it); read/write to the estimating shares and read to W: by UNC path (\\server\share, not a drive letter).
  6. Power and lock policy: no sleep, no hibernate, no screen lock, no screensaver, exempt from any domain lock policy — SOLIDWORKS and Excel need a live desktop session.
  7. Firewall on VM 1: allow the estimating portal (8071), Drawing Search (5000) and Client Briefing's port from the office network; allow the COM tools' port from the Linux VM only.
  8. Windows Update on VM 1: restarts scheduled out of hours and announced to James.
  9. A tscon hand-back script on the runner's desktop, and James shown the Hyper-V console route in.

VM 2 (Linux): Technical Design

  1. Create it as Generation 2 with Secure Boot on the Microsoft UEFI Certificate Authority template; no virtual TPM needed. 8 virtual CPUs, 32 GB memory, a 1 TB+ virtual disk on NVMe that can be grown; automatic start with the host.
  2. Ubuntu LTS server, fixed IP and DNS name on the External switch, SSH open to the Technical Design team with sudo accounts, fully updated. No graphics card.
  3. Firewall on VM 2: GitLab (80/443, and its git-over-SSH port) and the FastAPI services' port from the office network; PostgreSQL (5432) from VM 1 only.
  4. A read-only mount of W: for the FastAPI services (a service account on the file server; the credentials kept on the VM, not in any script).

Running it

  1. Licences: Windows Server 2025 Standard per core (two 16-core packs for the 9975WX) and client access licences; one Windows 11 Pro and one Office licence for VM 1; nothing for the Linux VM.
  2. Backups: host and both VMs (Windows Server Backup or the company tool, with the VMs exported); the Design Vault's GitLab backup on its own schedule; one restore of each tested before go-live.
  3. Windows Update: host and VM 1 on different nights, James told first. Ubuntu's security updates unattended, reboots announced.
  4. Antivirus: apply the exclusions James supplies (SOLIDWORKS temp, the output folders, Drawing Search's index).
  5. Power: on the UPS, set to start again after a power cut, both VMs starting automatically.

Handover checks

Jack confirms these, then the machines are James's:

  • In VM 1's Device Manager the graphics card shows as NVIDIA RTX 4000 Ada with the NVIDIA driver, not "Microsoft Basic Display".
  • After a full restart of the host, both VMs start by themselves; VM 1 logs in as the runner account with nobody touching it and is still unlocked an hour later.
  • Signed in as the runner account, VM 1 can open and save a file in the estimating folders and open a file on W: by UNC path.
  • From VM 1, the licence manager on the host answers on port 25734.
  • From a desk, VM 1 answers on ports 8071 and 5000 (once James's services run, this is just a browser test); from the Linux VM, VM 1 answers on the COM tools' port.
  • From James's laptop: Remote Desktop to the host as an administrator while another admin is already connected; the Hyper-V console shows VM 1's desktop; SSH into the Linux VM by name, and the W: mount lists a job folder.

Everything that makes it an SDI Intelligence machine, installed the same way as on the laptop. The Technical Design team does the Linux side with James.

  11. Hand Jack the antivirus exclusion paths and the ports to open.

On VM 2 (Technical Design), with the Technical Design team

  1. GitLab with LFS on its own address or port, with backups scheduled; the SDI Design Vault's repositories created.
  2. PostgreSQL for the Document Manager's intelligence layer, reachable from VM 1 only.

Proving the whole

  1. Run one known job (12645 or 12173) on VM 1 and compare the book and the run time with the laptop's.
  2. Restart the host and confirm both VMs, the portal, the runner, Client Briefing, Drawing Search and the Linux services all come back without anyone logging in.
  3. Remote in and out once through the Hyper-V console while a short job runs on VM 1, and confirm the job finished.
  4. Retire the laptop's role: the laptop becomes a development machine; the installed service and runner on it are stopped so there is one queue.
