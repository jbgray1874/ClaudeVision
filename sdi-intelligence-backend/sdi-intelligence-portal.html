AI Tools & Key Python Files

The modules that decide an estimate — what each does, what it reads, what it writes, and which database tables and spreadsheets it touches. Run commands are from the engine host. Not every file in src\ is here, and deliberately so: the folder also holds one-off probes (prefixed _), superseded copies and diagnostics that nothing in the pipeline calls. What follows is what runs.

Entry Points

main.pyEntry Point
The top-level runner. Accepts a job folder, orchestrates the full pipeline: PDF+DXF scan → SolidWorks native read → canonical BOM and route → per-part estimates → the populated estimating workbook (Estimate, Decision Report, AI Provenance) + JSON + deliverable HTML + audit log. Tim JSON overrides are intentionally absent — all pricing must come from drawings and the database.
python -u main.py --search-root "K:\Estimating\AI Estimating\Live Enquiry\1282..." --folder-as-job
Reads: job folder PDFs/DXFs via file_scan.py
Writes: C:\ClaudeVision\output\estimates\ xlsx + JSON; AIEstimating.ScanLog
No longer reads: job_bought_in_materials.json, job_assembly_labour.json (backed out — data must come from drawings)
file_scan.pyCore Orchestrator
The engine's inner loop. For each job folder: calls extractor_patterns to parse BOM rows from PDFs, calls bom_table_extractor + bom_tree to resolve GA → sub-assembly → detail quantities, stamps per-bay quantities onto parts, calls estimator.py for each part, assembles estimate_document, then calls bay_rollup.py. Builds the catalogue_pricer chain: price_book → UDEF → web/AI.
Calls: extractor_patterns, bom_table_extractor, bom_tree, estimator, bay_rollup, xlsx_output
DB reads: none directly — delegates to pricing_service.py
Writes: per-page bom_table_rows in summary JSON
estimate_full_parity_report.pyReady
Full parity bundle comparing the engine output line-by-line against the manually completed workbook. Writes HTML + JSON + CSV per drawing under the outputs share. Used by JR and the team to validate each run.
python estimate_full_parity_report.py "1282"
Reads: engine JSON output + manual xls from K:\Estimating\Completed\Manual Estimates\
Writes: C:\ClaudeVision\output\parity\

Drawing Extraction

extractor_patterns.pyPDF/DXF Parser
Extracts BOM rows, title block data (drawing number, revision, client, material, finish) and part metadata from PDFs and DXFs. Uses pattern matching + LLM fallback for garbled text. The primary source for all part descriptions — no data comes from manual spreadsheets.
Reads: PDF/DXF files from job folder
Exports: bom_rows, title_block, normalized_material, normalized_geometry in summary dict
LLM calls: xAI Grok vision for difficult PDFs (api.x.ai), cached per page; falls back gracefully. Anthropic is used separately for the bought-in price lookup, not for reading pages.
bom_table_extractor.pyBOM Grid Reader
Reads BOM tables by grid structure rather than raw text, recovering wrapped two-line part numbers that text-order extraction scrambles. Critical for GA drawings where items like "1448-01" split across lines. This is the correct source for all part quantities.
Input: PDF page object
Output: structured list of BOM rows with item, drawing ref, description, qty — tagged FOLLOW or PRICE
bom_tree.pyQuantity Resolver
Resolves effective per-bay quantities by multiplying parent GA quantities into sub-assembly children. GA BOM references sub-assembly drawing → sub-assembly has per-unit qty → detail DXF provides geometry. Effective qty = product down the path. Ensures the engine prices the right number of parts per bay.
Key functions: resolve_effective_quantities(), merge_table_bom_rows()
Wired in: file_scan.py line ~1510 — stamps quantities before estimate_document
drawing_inspector.pyDiagnostic
Test harness — run against any drawing pack to see drawing number, revision, client, material, and all BOM rows tagged FOLLOW or PRICE. Use this to verify a new job's drawings are being parsed correctly before running a full estimate.
python drawing_inspector.py "K:\Estimating\AI Estimating\Live Enquiry\1282..."
Writes a human-readable report to console. No DB writes.
bom_quantity_audit.pyDiagnostic
Safety-net — flags every part whose per-bay quantity has no governing BOM row. Use after any new job to ensure the BOM tree resolved correctly and no parts are being priced at the wrong quantity.
python bom_quantity_audit.py "K:\Estimating\AI Estimating\Live Enquiry\1282..."
Writes a CSV of flagged parts. No DB writes.

Pricing Engine

pricing_service.pyCore Pricer
The heart of the pricing chain. Walks every part through the full tier chain (see RAG Lookup Chain below). Holds _get_udef_anchor(), _get_pma_purchased(), _get_historical_rag(), _get_supplier_catalog(), _get_web_ai_fallback(). All DB connections via pyodbc to SDILive 10.0.0.200.
DB reads: dbo.UDEF_PARTS_TABLE_FOR_ESTIMATING, dbo.PMA_TBL, dbo.bought_in_parts, dbo.historical_quote_material_line, dbo.historical_quote_header, dbo.historical_quote_part, dbo.historical_quote_operation, dbo.labour_rates, dbo.estimating_supplier_catalog_url
External: Anthropic API for web/AI fallback (config flag: enable_web_ai_fallback)
estimator.pyPart Pricer
Prices individual fabricated parts. Resolves system cost via RAG (_resolve_part_system_cost()), applies implausibility caps (fixings capped at £10 from RAG), handles description noise guard (descriptions ≤ 2 chars blanked to prevent phantom SSH matches). Powder coat priced via bars/hr model (319/191/127 by thickness).
DB reads: via pricing_service.py
Fixing cap: SSH-, M[0-9], FIXING, NUT, BOLT, SCREW etc. capped at £10 unit from RAG
RAG corpus: dbo.historical_quote_material_line joined to historical_quote_header (1,982 jobs: M&S 777, Boots 333, TTI 316, Tesco 243)
bay_rollup.pyBay Aggregator
Rolls up all parts into bay-level cost lines. Prices catalogue tokens (ELECTRICS, FIXING*, SLOTTEDTUBE*, VINYL*, SUBPLAS*) via the catalogue_pricer chain. As of 24 June 2026, the chain is: price book → UDEF → web/AI. UDEF has the entire 1282 BOM at correct prices with supplier names.
Catalogue token chain (in order):
1. Price book JSON (historical RAG, built by corpus_ingest)
2. dbo.UDEF_PARTS_TABLE_FOR_ESTIMATING — 15,118 priced items. Exact code match → description token overlap
3. Web/AI fallback (indicative, clearly flagged, config flag required)
4. Unpriced flag with specific reason
Module-level cache: _SYSTEM_COST_NO_MATCH prevents repeat SQL calls; _MAX_SYSTEM_COST_VARIANTS = 3 caps description variants
bought_in_pricing.pyCatalogue Pricer
Builds the price-book pricer from the RAG corpus JSONL. Matches BOM tokens (ELECTRICS, FIXING5 etc.) to historical prices by exact code then description containment. Returns a priced dict or a miss dict — never guesses. Used by file_scan.py to construct the combine_pricers() chain passed into bay_rollup.
Reads: C:\ClaudeVision\output\price_book.json (built from corpus)
Key functions: make_price_book_pricer(), combine_pricers(), load_cached_price_book()

Arbitration & Assurance

Where the engine decides which of several readings it believes, and whether the result may be quoted. This layer is what separates a number from a defensible number, and it did not exist when this page was first written.

source_precedence.pyThe Waterfall
Ranks every source that can state a value — SolidWorks model, DXF, drawing text, BOM, inference, LLM — and decides which wins. Crucially it also RECORDS what it displaced, so a disagreement can be reported afterwards instead of being silently overwritten.
Reads: each part's competing readings
Writes: the winning value plus _displaced on the part
route_compiler.pyCanonical Route
Compiles one decision per operation per part: is it required, not applicable, or unverified, and on whose authority. Contested decisions — where two equally-ranked sources disagreed — are recorded with the losing claim named, and surface on the Decision Report tab.
Reads: parts, BOM hierarchy, drawing cues
Writes: canonical_route_shadow in the job JSON
invariants.pyThe Gate
The checks that decide whether a job may go out as a firm price. Each returns BLOCKING (the figure is not safe to quote), WARNING (a judgement for the estimator) or UNVERIFIED (the check could not run). Nothing is silenced: a material with no rate, a cut path that cannot fit its blank, a BOM naming a drawing the pack does not contain — all reach the reader.
Reads: the finished job summary
Writes: summary["invariants"]; the Estimating Review block in the run log
costed_facts.pyOne Reader
The single source for facts every deliverable must agree on — blank dimensions, per-part material cost, which parts are board rather than steel, and which BOM lines have no drawing. It exists because the same question answered separately in four modules is how two documents from one run came to contradict each other.
Reads: the job summary
Writes: nothing — it is a reader, and that is the point
price_provenance.pyWhere the Money Came From
Classifies every applied price: an agreed rate, a catalogue line, a purchase history, or a generated market estimate. Reproducibility and firmness are tracked separately — a list price repeats perfectly and commits nobody.
Reads: each priced line
Writes: provenance and firmness stamps read by the quote and the invariants
confidence.pyField Confidence
Per-field strength for each part — CONFIRMED, MEASURED, REPORTED, ASSUMED or UNKNOWN — scored on the field's own source rather than an average. The AI Provenance tab reads this, and reports how well the drawings were READ separately from how much has been PRICED.
Reads: each part's sources
Writes: the assessment behind the AI Provenance tab

Output & Reporting

wb_populate.pyThe Workbook
Populates SDI's own estimating template — the Estimate tab an estimator edits. Writes Excel FORMULAS rather than values, so the sheet recalculates when a rate is changed. Labour is grouped by tooling setup, outstanding estimator inputs are listed and shaded, and BOM lines whose drawings were never supplied are named so the total is not read as covering them.
Reads: the canonical BOM and route
Writes: the populated .xlsx
estimation_report.pyAI Provenance tab
The per-part account of where every value came from and how strong it is. Its summary separates what the engine READ from what has been PRICED — an estimate is expected to arrive with rates outstanding, and folding that into one confidence band made a fully-read job read as a failure.
Reads: the job summary and confidence assessment
Writes: the AI Provenance sheet
job_decision_report.pyDecision Report tab
What the engine decided and on whose authority — plus the arguments it had to settle: operations where equally-ranked sources disagreed, and the costlier ones about material and gauge, widest disagreement first.
Reads: the canonical route and the invariants
Writes: the Decision Report sheet
job_report_html.pyInternal Job Report
The narrative deliverable — what went right, the review items, the drawing-pack audit including drawings named on the BOM but absent from the pack, and the failed checks in plain English. The best single document for judging whether an estimate is safe to quote from.
Reads: the job summary
Writes: <job>_report.html
client_quote_html.pyCustomer Quotation
The document that leaves the building. Deliberately the plainest of the set: price, specification, what is included. The engine's reasoning — invariant names, confidence, the gap list — is kept off it; scope is the estimator's to state in their own words.
Reads: the job summary
Writes: <job>_quote.html
client_quote_regen.pyEstimator Override
Turns an estimator's AMENDED workbook back into a client quote. Reads their own figure off the saved sheet (Sell Price in preference to Unit Cost), reloads the original job so the material, finish, operations and GA survive, and files the sheet as the manual-override record. No engine re-run, no drawing re-read.
Reads: the amended .xlsx + the job's saved JSON
Writes: the regenerated quote and <job>_MANUAL_OVERRIDE.xlsx
xlsx_output.pyWorkbook Writer
Writes the five-sheet estimate workbook. Populates Customer, Description and Revision from per-page title blocks (not from manual sheets). GA revision appears in the output filename (e.g. _RevA). Customer noise filter rejects garbled disclaimer text. Quality Summary tab auto-attaches via quality_summary.py.
Writes: C:\ClaudeVision\output\estimates\{job}_{RevX}.xlsx
Sheets: Steel Parts · Bought-In · Labour · Summary · Quality Summary
No longer reads: _load_bought_in_for() stubbed — returns empty (Tim JSON backed out)
Customer field priority: derived_client (cell model) → pdf fallback → title block
quality_summary.pyQA Tab
Produces the Quality Summary fifth tab. Classifies parts as manufactured vs bought-in by nature (not pricing route). Reports real geometry-source counts, flags with plain-English descriptions, and shows per-part confidence. Wired to auto-attach inside write_estimate_xlsx.
Flag fields: extracts reason from dict flags (not raw dict repr)
Geometry source: checks normalized_geometry, material_estimate, cut_length fallback
Qty source: reads assumed_job_quantity from estimate_workbook_inputs
corpus_ingest.pyRAG Builder
Turns historical SDI estimate workbooks into the RAG corpus. Parses steel parts, bought-in lines and labour from each xls/xlsx. Outputs to a JSONL file — a separate loader script writes this into dbo.historical_quote_* tables. The 1,982-job corpus (M&S 777, Boots 333, TTI 316, Tesco 243) was loaded 18 June 2026 and is live.
python corpus_ingest.py --glob "K:\Estimating\Completed\**\*.xls*" --out corpus.jsonl
Reads: historical xls/xlsx workbooks from K: drive
Writes: JSONL file → loaded into dbo.historical_quote_header, dbo.historical_quote_material_line, dbo.historical_quote_part, dbo.historical_quote_operation

Database Tables

All tables on 10.0.0.200 · SDILive · UID AIBot · ODBC Driver 18 · pyodbc only. The dbo schema is the live ERP — read-only. AIEstimating is the engine's writable workspace. Every column name and row count below was verified by direct SQL query on 24 June 2026.

dbo — ERP read-only AIEstimating — engine writable
dbo.UDEF_PARTS_TABLE_FOR_ESTIMATINGTier 1 · PRIMARY
The single most important pricing table. 20,015 rows, 15,118 with prices. Contains the entire SDI bought-in catalogue — every ELEC*, FIXING*, SLOTTEDTUBE*, VINYL*, SUBPLAS*, SSH-* code SDI has ever bought. The complete 1282 Milwaukee BOM is here: ELEC-50CM LOOM £23.00 (Elite Sourcing), FIXING5 £0.01, SLOTTEDTUBE01/02 £3.57 (Preferred Tubes), SUBPLAS72 £1.00 (Eagle Plastics), VINYL03/76 £0.85 (Chartwell Press). Collation: Latin1_General_BIN (binary, case-sensitive).
Confirmed columns: [Part code] varchar(16), [Part rev] varchar(4), [Description] varchar(200), [UOM] varchar(4), [Proc code] varchar(1), [System cost per] decimal(9,2), [Sales Price per] decimal(18,5), [Supplier code] varchar(10), [Supplier name] nvarchar(80), [WO Est lab cost], [WO Est mat cost], [WO Actual lab cost], [WO Actual mat cost]
Engine query: exact [Part code] match (conf 0.95) → description LIKE ≥8 chars (conf 0.82)
Now also used for: catalogue tokens (ELECTRICS, FIXING*, SLOTTEDTUBE* etc.) when price book misses — wired into bay_rollup.py catalogue token chain 24 June 2026

Self-Improvement

Learning Loop

Every estimator correction makes future estimates more accurate. A human fix becomes a permanent engine improvement in three stages.

Stage 1 · Pre-scan
Inject known-correct values
Before pricing, learning_engine.py checks PartKnowledge for a matching pattern at confidence ≥ 0.8. If found, correct material, thickness and price are injected — never re-derived.
Stage 2 · Post-scan
Detect and flag anomalies
After each run the engine scans for known problem patterns — zero_cost_steel, unknown_material, thickness anomalies — and writes them to Corrections with context for estimator review.
Stage 3 · Promotion
Confirm → permanent fix
When a correction reaches three occurrences (confidence 0.85) it auto-promotes to LiveOverrides — firing immediately on every future scan without any code change.
Correction → Corrections → (×3) → PartKnowledge + LiveOverrides → injected at next pre_scan

The testing procedure

Four stages. Each one names who holds it.

1  ·  Set up and run the jobJames Gray
Checks the Live Enquiry Log, collects the drawings from the Design & Production folders, creates a new folder in Live Enquiry, and uploads the drawings into the tool.
A run takes between 10 minutes and 2 hours depending on how many drawings there are and how complex the job is. That is expected, not a fault — plan around it rather than chasing it.

When it finishes the folder contains three things:
  • A populated estimating sheet — the one you work in
  • A generated quote ready to send to the customer
  • An HTML report setting out how the AI reached the estimate
James then e-mails estimating@wearesdi.com to say the folder is ready. Nothing is expected from you until that e-mail arrives.
2  ·  Review and amendEstimating team
Work from the populated estimating sheet with the drawings alongside it. Put any changes into that same spreadsheet — not into a new one, not into an e-mail — and send it back to James.
Save it in Excel before you send it. The totals are formulas and Excel only writes the computed values on save. The tool will tell you if this was missed rather than produce a blank quote, but it costs a round trip.

Changing a number in the sheet is the feedback — it is what the parity report at stage 3 is built from. You do not need to write an explanation at this stage; you will be asked about the differences that matter.
3  ·  Regenerate and run parityJames Gray
Uploads your amended estimate into the tool and regenerates the customer quote. Then runs a parity report between the two estimates and sends the queries — why did these change? — to estimating@wearesdi.com.
Filing convention, so the folder stays readable:
  • The amended spreadsheet is saved in the folder as V2
  • The updated client quote overwrites the original — deliberately not versioned, because nothing going to a customer should say V2
4  ·  Answer the parity queriesEstimating team · 7 working days
Review that week's parity reports and send answers back to James within 7 working days.
This is the stage the whole thing exists for. A changed number tells us that the engine was off; your answer tells us why, and that is what lets the model be retaught so the same problem stops recurring. It is also the one place where differences between how each of us estimates become visible, which is worth having in its own right.

Training — one hour, before this starts

A one-hour session, run by James Gray and Charlotte Blackwell, covers what each report means and what is needed from you when sending notes back on a parity report. If you take one thing from this page: the answers at stage 4 are the deliverable, and they are what the 4 September gate is evidenced on.

How a datum is decided — the source waterfall

      
Every source that can say something about a part is read, and none is trusted blindly. Each carries a rank. The rule is absolute, and it is the reason the engine can be audited: a weaker source may FILL a datum, it may never REPLACE a stronger one — and where two disagree, the disagreement is written onto the part and the stronger value kept. Nothing is decided by whichever pass happens to run last.

        report, AI Provenance, Decision Report) read from that one costed-facts layer, which is why they cannot
        contradict each other.

The queue, and the mistake it was made to prevent

        A run is claimed (POST /runner/claim), reports progress, then completes —
        so a run that dies with the laptop is visible as abandoned rather than appearing to hang for ever. Inputs

        from under the estimate that was mid-flight. The refusal names the run in front of you and offers to
        release it.


        Selection is the estimate. The folder is not read wholesale; what was staged is what was priced,
        and the job report names every file read and every file present-but-not-read.

Amend the sheet, upload it, get a fresh quoteBuilt & working

          
This is the loop Week One is built on. You take the pre-populated sheet, put your own figures in it, send it back, and a new client quotation comes out carrying your number. Nothing is re-run and no drawings are needed.

          

            

              1Open the pre-populated workbook and fill in what is yours to settle — the outstanding inputs, and any figure you disagree with.
              2Save it in Excel before you send it. The totals are formulas and Excel only writes the computed values on save. If you skip this the tool says so rather than producing a blank quote — but it costs you a round trip.
              3Upload it on the estimating page and re-enter units, drawing number and client. Hours or days later is fine.
              4Out comes a full client quotation — material, finish, operations and the GA image are carried over from the original run, with only the money and those three fields overlaid.
            

            

              Your figure is the one that goes out. The sheet is read for Sell Price in
              preference to Unit Cost, so a margin you set is what the customer sees. Your sheet is kept as the
              record, filed as <job>_MANUAL_OVERRIDE.xlsx next to the quote on the AI Estimating share
              — so six weeks later there is a record of what you changed and why the quote says what it says.
            

          

        


        
        

          
⚠ INSUFFICIENT DATA — what it meansDo not quote

          
When the engine suppresses a job it means it doesn't have enough confident geometry or pricing to produce a number it would stand behind. The headline total is blanked — it is not for quoting. This is the engine being honest, not broken.

          

            Common reasons a job is suppressed:
            
    
              
  • Low DXF coverage — fewer than ~60% of parts have a DXF file. Without flat-pattern geometry the engine can't measure area, weight or cut length reliably.
    • 
              
  • Wire / mesh parts — wire goods (baskets, grids) don't have flat DXFs by design. The engine flags these as insufficient rather than guess.
    • 
              
  • No drawing pack — if the folder contains only a GA drawing and no part drawings, coverage will be very low.
    • 
              
  • Drawings named on the BOM but not supplied — the engine prices what it was given and states the gap: a red DRAWINGS MISSING FROM THIS PACK block on the Estimate sheet, a line on AI Provenance, and NOTHING DECIDED, NOTHING COSTED on the Decision Report, each naming the parts. A thin total on an incomplete pack is an incomplete pack, not a cheap job — ask for the detail drawings before quoting the whole product.
    • 
              
  • Unknown materials — if the engine can't determine the material for most parts it suppresses rather than cost them wrong.
    • 
            

            What to do: Check the Decision Report — it shows credibility % and flags exactly which parts are the problem. If the job has DXFs that weren't found, check the folder structure and re-run. If the job is genuinely wire goods, the wire model is the fix (in development).
          

        


        
        

          
ConfidenceOn every part

          
The AI Provenance tab names how each value was arrived at, field by field, rather than reducing a part to a single number. A score hid which half of a part was weak; the source does not.

          

            

              CONFIRMEDAn estimator has already agreed this, and it was remembered.
              MEASUREDRead off the SOLIDWORKS model or a DXF flat pattern — a measurement, not a reading.
              REPORTEDPrinted on the drawing or in the BOM. Reliable, but it is what someone typed.
              ASSUMEDA default or an inference is standing in. Worth a glance.
              UNKNOWNNothing supplied it. On a price this means nobody has priced it yet.
            

            

              Read and priced are two different questions. The tab reports them
              separately — how well the engine read the drawings, and how many lines are still awaiting your
              rate. An estimate is expected to arrive with prices outstanding; that is not a fault in the
              reading. See the SDI Estimating Intelligence Guide.
            

          

        


        
        

          
Outstanding inputs, and why a price may not be reproducibleRead before quoting firm

          
Every sheet arrives with a count of inputs outstanding — the lines the engine holds no rate for, or where a figure is only yours to settle. That number is not a fault in the reading; it is the sheet telling you which part of it is genuinely yours to finish.

          

            On the jobs run this fortnight it ran three on the Side Panel, four on 12392-02, six on 12422-24 and
            eight on the Fragrance Coffret — almost all of them bought-in prices the engine has no catalogue
            rate for.
            

              Where there is no catalogue price, the engine uses a market estimate.
              That figure is real and it is clearly labelled — but it is not reproducible: the same job can
              price differently on the same inputs. Every job carrying one raises a blocking finding that
              says so. Treat a market-estimate line as a number to confirm, not a number to quote.
            

            

              A £0 line never means free. If the engine can derive no blank, mass or
              section it flags the part cost not derivable rather than costing it at nothing.
            

            

              This is the number that falls permanently. Items SDI buys under a code
              are already priced live from the UDEF purchasing catalogue. Every further supplier catalogue
              loaded removes outstanding inputs from every future job — which is why the key supplier list is
              the ask that most reduces your own workload.
            

          

        


        
        

          
How to submit a correctionFeeds the learning engine

          
When you spot something wrong — wrong material, wrong thickness, wrong process, wrong price — tell James. Every correction gets logged and at three occurrences becomes a permanent engine fix. This is how the engine gets better over time.

          

            The standard form and return route are not built yet. Until they are,
            this is an e-mail to James with the five fields below. That informality is not a detail — the 19 August
            report names the missing return route as the direct cause of zero feedback: twelve of nineteen
            estimates have drawn no response at all, and nothing has come back since 28 July. It is eight hours of
            work and it is the item that unblocks the whole programme's leading indicator.


            One thing that is already known to work: estimates sent to a single
            named person are answered 50% of the time; those sent to two names at once, 14%.
            Shared ownership is measurably no ownership — so if a sheet arrives addressed to you and someone else,
            agree between you who has it.

  • Job number — e.g. 12464
    • 
              
  • Part number — e.g. 12464-01-20A
    • 
              
  • What the engine said — material / thickness / process / cost
    • 
              
  • What it should be — the correct value
    • 
              
  • Source — title block, supplier quote, your own knowledge

Known limitationsIn development

          
Areas where the engine currently suppresses or produces less reliable numbers. These are known and being addressed — not gaps to work around, but to be aware of during the parallel run.

          

            
    
              
  • Wire and mesh goods — baskets, grids, wire frames. These structurally have no flat DXFs. A dedicated wire costing model is in development.
    • 
              
  • Weldments and tube — the engine now reads the weldment cut list from the model, so a welded frame is priced from its real bar sections instead of being absent. That reader is written and tested offline but needs a SOLIDWORKS seat to be proven end to end, so it is not in play this week. Without it, bounding-box area still under-estimates powder coat on complex weldments — pass items_per_bar=1 + real area as a manual override.
    • 
              
  • No-DXF jobs — jobs where drawings exist only as PDFs. The engine produces a suppressed estimate and flags it loudly.
    • 
              
  • Bends on Base Flange parts — where the model bakes its bends into the sketch, the part is flagged formed, bend count unreadable rather than silently counted flat. A part so flagged needs your eye on the fold count.
    • 
              
  • Hand-drawn packs and TTi — not yet run with an estimator at all. Hand-drawn is recommended for explicit exclusion from v1.
    • 
              
  • Powder coat setup cost — the throughput model is built but not yet wired into the estimator. Current powder numbers will move when it goes live.
    • 
              
  • PET / PETG plastic parts — now route to the acrylic sheet path rather than to steel, which was the costly error. The remaining approximation is that PETG is priced as acrylic rather than on its own rate (json_normaliser.py).
