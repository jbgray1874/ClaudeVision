AI Tools & Key Python Files

Every module in C:\ClaudeVision\src\ documented — what it does, what it reads, what it writes, and which database tables and spreadsheets it connects to. Run commands are from the engine host.

Entry Points

main.pyEntry Point
The top-level runner. Accepts a job folder, orchestrates the full pipeline: PDF+DXF scan → BOM tree → per-part estimates → bay rollup → five-sheet xlsx workbook + JSON + audit log. Tim JSON overrides are intentionally absent — all pricing must come from drawings and the database.
python -u main.py --search-root "K:\Estimating\AI Estimating\Live Enquiry\1282..." --folder-as-job
Reads: job folder PDFs/DXFs via file_scan.py
Writes: C:\ClaudeVision\output\estimates\ xlsx + JSON; AIEstimating.ScanLog
No longer reads: job_bought_in_materials.json, job_assembly_labour.json (backed out — data must come from drawings)
file_scan.pyCore Orchestrator
The engine's inner loop. For each job folder: calls extractor_patterns to parse BOM rows from PDFs, calls bom_table_extractor + bom_tree to resolve GA → sub-assembly → detail quantities, stamps per-bay quantities onto parts, calls estimator.py for each part, assembles estimate_document, then calls bay_rollup.py. Builds the catalogue_pricer chain: price_book → UDEF → web/AI.
Calls: extractor_patterns, bom_table_extractor, bom_tree, estimator, bay_rollup, xlsx_output
DB reads: none directly — delegates to pricing_service.py
Writes: per-page bom_table_rows in summary JSON
estimate_full_parity_report.pyReady
Full parity bundle comparing the engine output line-by-line against the manually completed workbook. Writes HTML + JSON + CSV per drawing under the outputs share. Used by JR and the team to validate each run.
python estimate_full_parity_report.py "1282"
Reads: engine JSON output + manual xls from K:\Estimating\Completed\Manual Estimates\
Writes: C:\ClaudeVision\output\parity\

Drawing Extraction

extractor_patterns.pyPDF/DXF Parser
Extracts BOM rows, title block data (drawing number, revision, client, material, finish) and part metadata from PDFs and DXFs. Uses pattern matching + LLM fallback for garbled text. The primary source for all part descriptions — no data comes from manual spreadsheets.
Reads: PDF/DXF files from job folder
Exports: bom_rows, title_block, normalized_material, normalized_geometry in summary dict
LLM calls: Claude vision for difficult PDFs; falls back gracefully
bom_table_extractor.pyBOM Grid Reader
Reads BOM tables by grid structure rather than raw text, recovering wrapped two-line part numbers that text-order extraction scrambles. Critical for GA drawings where items like "1448-01" split across lines. This is the correct source for all part quantities.
Input: PDF page object
Output: structured list of BOM rows with item, drawing ref, description, qty — tagged FOLLOW or PRICE
bom_tree.pyQuantity Resolver
Resolves effective per-bay quantities by multiplying parent GA quantities into sub-assembly children. GA BOM references sub-assembly drawing → sub-assembly has per-unit qty → detail DXF provides geometry. Effective qty = product down the path. Ensures the engine prices the right number of parts per bay.
Key functions: resolve_effective_quantities(), merge_table_bom_rows()
Wired in: file_scan.py line ~1510 — stamps quantities before estimate_document
drawing_inspector.pyDiagnostic
Test harness — run against any drawing pack to see drawing number, revision, client, material, and all BOM rows tagged FOLLOW or PRICE. Use this to verify a new job's drawings are being parsed correctly before running a full estimate.
python drawing_inspector.py "K:\Estimating\AI Estimating\Live Enquiry\1282..."
Writes a human-readable report to console. No DB writes.
bom_quantity_audit.pyDiagnostic
Safety-net — flags every part whose per-bay quantity has no governing BOM row. Use after any new job to ensure the BOM tree resolved correctly and no parts are being priced at the wrong quantity.
python bom_quantity_audit.py "K:\Estimating\AI Estimating\Live Enquiry\1282..."
Writes a CSV of flagged parts. No DB writes.

Pricing Engine

pricing_service.pyCore Pricer
The heart of the pricing chain. Walks every part through the full tier chain (see RAG Lookup Chain below). Holds _get_udef_anchor(), _get_pma_purchased(), _get_historical_rag(), _get_supplier_catalog(), _get_web_ai_fallback(). All DB connections via pyodbc to SDILive 10.0.0.200.
DB reads: dbo.UDEF_PARTS_TABLE_FOR_ESTIMATING, dbo.PMA_TBL, dbo.bought_in_parts, dbo.historical_quote_material_line, dbo.historical_quote_header, dbo.historical_quote_part, dbo.historical_quote_operation, dbo.labour_rates, dbo.estimating_supplier_catalog_url
External: Anthropic API for web/AI fallback (config flag: enable_web_ai_fallback)
estimator.pyPart Pricer
Prices individual fabricated parts. Resolves system cost via RAG (_resolve_part_system_cost()), applies implausibility caps (fixings capped at £10 from RAG), handles description noise guard (descriptions ≤ 2 chars blanked to prevent phantom SSH matches). Powder coat priced via bars/hr model (319/191/127 by thickness).
DB reads: via pricing_service.py
Fixing cap: SSH-, M[0-9], FIXING, NUT, BOLT, SCREW etc. capped at £10 unit from RAG
RAG corpus: dbo.historical_quote_material_line joined to historical_quote_header (1,982 jobs: M&S 777, Boots 333, TTI 316, Tesco 243)
bay_rollup.pyBay Aggregator
Rolls up all parts into bay-level cost lines. Prices catalogue tokens (ELECTRICS, FIXING*, SLOTTEDTUBE*, VINYL*, SUBPLAS*) via the catalogue_pricer chain. As of 24 June 2026, the chain is: price book → UDEF → web/AI. UDEF has the entire 1282 BOM at correct prices with supplier names.
Catalogue token chain (in order):
1. Price book JSON (historical RAG, built by corpus_ingest)
2. dbo.UDEF_PARTS_TABLE_FOR_ESTIMATING — 15,118 priced items. Exact code match → description token overlap
3. Web/AI fallback (indicative, clearly flagged, config flag required)
4. Unpriced flag with specific reason
Module-level cache: _SYSTEM_COST_NO_MATCH prevents repeat SQL calls; _MAX_SYSTEM_COST_VARIANTS = 3 caps description variants
bought_in_pricing.pyCatalogue Pricer
Builds the price-book pricer from the RAG corpus JSONL. Matches BOM tokens (ELECTRICS, FIXING5 etc.) to historical prices by exact code then description containment. Returns a priced dict or a miss dict — never guesses. Used by file_scan.py to construct the combine_pricers() chain passed into bay_rollup.
Reads: C:\ClaudeVision\output\price_book.json (built from corpus)
Key functions: make_price_book_pricer(), combine_pricers(), load_cached_price_book()

quality_summary.pyQA Tab
Produces the Quality Summary fifth tab. Classifies parts as manufactured vs bought-in by nature (not pricing route). Reports real geometry-source counts, flags with plain-English descriptions, and shows per-part confidence. Wired to auto-attach inside write_estimate_xlsx.

Key principle — no data from manual spreadsheets

Tim's completed estimate sheets, bought-in BOM lines and assembly hours are not used as inputs. job_bought_in_materials.json and job_assembly_labour.json injection has been removed from main.py. tim_rate_card.json is retained as an offline fallback only (it encodes SDI pricing policy, not job-specific data). All bought-in prices come from dbo.UDEF_PARTS_TABLE_FOR_ESTIMATING (the live Access Supply Chain database), which has 15,118 priced SDI items. All part descriptions come from drawings.
Self-Improvement

Learning Loop

Every estimator correction makes future estimates more accurate. A human fix becomes a permanent engine improvement in three stages.

Stage 1 · Pre-scan
Inject known-correct values
Before pricing, learning_engine.py checks PartKnowledge for a matching pattern at confidence ≥ 0.8. If found, correct material, thickness and price are injected — never re-derived.
Stage 2 · Post-scan
Detect and flag anomalies
After each run the engine scans for known problem patterns — zero_cost_steel, unknown_material, thickness anomalies — and writes them to Corrections with context for estimator review.
Stage 3 · Promotion
Confirm → permanent fix
When a correction reaches three occurrences (confidence 0.85) it auto-promotes to LiveOverrides — firing immediately on every future scan without any code change.
Correction → Corrections → (×3) → PartKnowledge + LiveOverrides → injected at next pre_scan

Build Notes
Architecture & Security

        
How the estimating engine, the portal, the database and the file shares connect. Everything server-side — the browser never touches the VPN, the shares or the DB directly.


      
      

        
      


      

        
Security boundary

        The browser only ever talks to the FastAPI backend on port 8071 — same origin, no CORS complexity. The backend validates every request with X-SDI-Key, enforces UNC root containment on every file path, and is the only process that touches SDILive or the file shares. The browser never has credentials, never sees a UNC path directly, and never touches the VPN.

R&D Capture & Innovation Funding

        
A live record of SDI's qualifying research & development — captured month by month, as the work happens, to support tax relief claims and grant applications. Owner: James Gray · Finance: Charlotte Blackwell · Sponsor: Matt Evans (MD).


      
Why this exists

        Per the MD's directive (26 May 2026): capture a monthly summary of the work across the AI / Software / ERP workstreams, with costs and benefits, so R&D can be leveraged for tax efficiencies. Capturing as we go is far stronger — and cheaper — than reconstructing it at year-end, and is the best defence if HMRC raises an enquiry.


      

        
⚠ The deadline that can lose the claim — advance notification

        
If SDI has not made an R&D claim in the previous three years, HMRC requires an advance notification within 6 months of the end of the accounting period in which the R&D took place. Miss this window and the claim is lost entirely — regardless of how strong the underlying R&D is.

        
First action for Charlotte / specialist: confirm SDI's accounting-period end, confirm whether a claim was made in the last 3 years, and if not, diarise the 6-month notification deadline immediately. This is the single highest-priority item here.

      


      
The opportunity — two mechanisms, and they now stack

      

        

          
R&D Tax Relief
Merged scheme

          
For accounting periods from 1 Apr 2024 the SME & RDEC schemes merged into one. 20% above-the-line credit on qualifying spend — net ~15% after corporation tax, roughly £15,000 back per £100,000 of qualifying R&D. Loss-making R&D-intensive SMEs (≥30% of total spend) may instead use ERIS at up to ~27%.

        

        

          
Grant funding
No longer cancels relief

          
Under the merged scheme the old "subsidised expenditure" rule was dropped — a grant covering part of an R&D project no longer reduces the tax relief. Grants and tax relief now stack. Pursuing a Made Smarter or Innovate UK grant is additive to, not a trade-off against, the tax claim.

What the engine producesEvery run

          
For every job folder you point it at, the engine outputs a five-sheet Excel workbook plus a JSON audit file. The workbook is the deliverable — open it the same way you open a manual estimate.

          

            

              
Sheet 1

              
Estimate

              
The headline — unit cost, material sub-total, labour sub-total, rebate, overhead. If the job is suppressed, this sheet carries the ⚠ INSUFFICIENT DATA banner.

            

            

              
Sheet 2

              
Labour

              
Every operation per part — laser time, fold time, weld time, assembly, powder coat. Rate card source shown per line.

            

            

              
Sheet 3

              
Material Price Break

              
Material cost per part with the price source — which database tier the price came from, supplier, date.

            

            

              
Sheet 4

              
Decision Report

              
The engine's reasoning — one row per part showing material, thickness, operations, confidence score and the WHY for every decision. Start here if something looks wrong.

            

            

              
Sheet 5

              
AI Provenance

              
Full audit trail — every part, every price source, every rate. Includes the Rate / source column showing exactly where each number came from.

            

          

        


        
        

          
⚠ INSUFFICIENT DATA — what it meansDo not quote

          
When the engine suppresses a job it means it doesn't have enough confident geometry or pricing to produce a number it would stand behind. The headline total is blanked — it is not for quoting. This is the engine being honest, not broken.

          

            Common reasons a job is suppressed:
            
    
              
  • Low DXF coverage — fewer than ~60% of parts have a DXF file. Without flat-pattern geometry the engine can't measure area, weight or cut length reliably.
    • 
              
  • Wire / mesh parts — wire goods (baskets, grids) don't have flat DXFs by design. The engine flags these as insufficient rather than guess.
    • 
              
  • No drawing pack — if the folder contains only a GA drawing and no part drawings, coverage will be very low.
    • 
              
  • Unknown materials — if the engine can't determine the material for most parts it suppresses rather than cost them wrong.
    • 
            

            What to do: Check the Decision Report — it shows credibility % and flags exactly which parts are the problem. If the job has DXFs that weren't found, check the folder structure and re-run. If the job is genuinely wire goods, the wire model is the fix (in development).
          

        


        
        

          
Confidence scoresOn every part

          
Every part in the Decision Report carries a confidence score — how certain the engine is about that part's cost. The job-level credibility % is the weighted average across all parts.

          

            

              0.85 – 1.0DXF geometry confirmed, price from price book or ERP. High confidence — use the number.
              0.60 – 0.84PDF dimensions or partial geometry. Reasonable estimate — review the WHY column if the number looks off.
              0.30 – 0.59Historical RAG match or inferred geometry. Treat as a guide only — check the part manually.
              < 0.30Minimal information. The engine has flagged this part — do not rely on the cost without manual verification.
            

          

        


        
        

          
How to submit a correctionFeeds the learning engine

          
When you spot something wrong — wrong material, wrong thickness, wrong process, wrong price — tell James. Every correction gets logged and at three occurrences becomes a permanent engine fix. This is how the engine gets better over time.

          

            What to capture when you flag a correction:
            
    
              
  • Job number — e.g. 12464
    • 
              
  • Part number — e.g. 12464-01-20A
    • 
              
  • What the engine said — material / thickness / process / cost
    • 
              
  • What it should be — the correct value
    • 
              
  • Source — title block, supplier quote, your own knowledge
    • 
            

            The fix pipeline: Your correction → AIEstimating.Corrections → learning engine → at ×3 occurrences auto-promotes to LiveOverrides → fires on every future scan of a matching part. You correct it once, the engine remembers it permanently.
          

        


        
        

          
What the engine is good atStrong

          
Clean sheet-steel jobs with DXF drawing packs. The engine is most accurate when it has flat-pattern geometry for every part.

          

            
    
              
  • Flat sheet steel — laser cut, punched, folded parts with DXFs
    • 
              
  • Bought-in parts that appear in the price book (UDEF table or PMA)
    • 
              
  • Standard labour operations — laser, punch, fold, weld, assemble, powder coat
    • 
              
  • Multi-part assemblies where children have their own DXFs
    • 
              
  • Jobs SDI has priced before — historical RAG gives comparable pricing
    • 
            

          

        


        
        

          
Known limitationsIn development

          
Areas where the engine currently suppresses or produces less reliable numbers. These are known and being addressed — not gaps to work around, but to be aware of during the parallel run.

          

            
    
              
  • Wire and mesh goods — baskets, grids, wire frames. These structurally have no flat DXFs. A dedicated wire costing model is in development.
    • 
              
  • 3D welded assemblies — bounding-box area under-estimates powder coat on complex weldments. Pass items_per_bar=1 + real area as a manual override.
    • 
              
  • No-DXF jobs — jobs where drawings exist only as PDFs. The engine produces a suppressed estimate and flags it loudly.
    • 
              
  • Powder coat setup cost — the throughput model is built but not yet wired into the estimator. Current powder numbers will move when it goes live.
    • 
              
  • PET / PETG plastic parts — currently misrouted to MILD_STEEL on some jobs. Fix in progress (json_normaliser.py).
    •
