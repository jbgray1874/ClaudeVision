How Monday2Friday is built

Monday2Friday is a module of SDI Intelligence. It runs inside the same FastAPI service on the SDI Intelligence server, so it uses the same address, the same access key and the same network position next to the file shares and SDILive.

Overview

Pilot design: the tracker stays the source of truth

For the pilot, nobody has to stop using the tracker. Monday2Friday reads the workbook every time it changes and builds every screen from it, so the team tests real, current figures without a migration. What the tracker can't hold is kept in a small pilot store:

Held inWhat
Account trackerProjects, PMs, contacts, POs, costs, the monthly forecast and its colour-coded status, budgets, brands
Pilot storeForecast freezes, the reason and next action for each movement, the variations register, Kayleigh's answers, account owners, name spellings and deputies

When the open questions are answered, the import moves into the m2f schema on SDILive (m2f/schema_m2f.sql) and people update Monday2Friday instead of the tracker. The pilot store's contents carry across.

Projects are identified by tab and name, never by row number. Inserting one row in the tracker moved every later Boots row by one between the migration review and the current file, so row-based keys would have broken freezes, notes and variations.

Reading the tracker

  • Months get their year from each tab's own FYnn headers, walking the month sequence either side. Jan FY27 is January 2027, as the Forcasting Total sheet uses it.
  • Status comes from each tab's colour legend (Risk, TBC, Confirmed, Invoiced). Colours are compared as Excel displays them, with theme colours resolved through the workbook theme, so a theme green and the same RGB green count as the same status. Colours not on the legend stay Unclassified and go to Kayleigh.
  • Sub-accounts (Boots UK, Sigma) come from the row ranges the totals sheet adds up for each, not from fixed row numbers.
  • Nothing is guessed. Text that isn't clearly an amount, a project with no name, a value outside a total: each keeps its raw value and becomes a flagged item with a severity (decision, check or info).
  • Every column is kept. Known columns are mapped; every other column is kept under its own header, visible on the project panel.
  • Reconciliation. Each monthly total on the Forcasting Total sheet is re-added from the imported lines. On the current tracker every formula total matches to the penny, or differs by exactly an amount typed as text that Excel's own total ignores. The comparison is on Settings and data.

Data

Forecast figures

The dashboard's months are calendar months; the full year is the calendar year of the "as of" month, matching the tracker's FY labels. Totals include rows hidden in the tracker, because the tracker's own totals do; project lists leave hidden rows out unless asked. Status names follow Kayleigh's answer: if she confirms Confirmed means PO received and TBC means Awaiting PO, the boards switch to those names.

Target schema on SDILive

m2f.person, person_alias, account (Boots as parent of its divisions), project, forecast_line (one row per project per month), forecast_freeze and forecast_freeze_line, budget, variation, activity, and import staging (import_batch, stg_project, stg_forecast_line, import_issue). python -m m2f.db_load --schema creates it; it is safe to re-run.

Security

  • Every API call is checked against SDI_API_KEY, the same gate as the rest of SDI Intelligence. The pages themselves hold no data.
  • The key is kept in the browser's local storage. The portal's Monday2Friday button places it there, and the page asks for it if it's missing. It never appears in a URL.
  • The tracker is opened read-only. Uploads are limited to 25 MB and must be an .xlsx workbook.
  • Everything typed into the tracker is escaped before it is shown, so a cell can't inject script into the page.
  • Credit limits from the Brands tab are never sent to the browser.
  • The service account needs read access to the tracker's folder and write access to M2F_DATA_DIR only.
  • Writes (freezes, notes, variations, answers, owners) are recorded with the name the person gives. Proper sign-in through Entra ID, as planned for the portal, will replace that name.

Configuration

Two optional lines in the backend's .env:

M2F_TRACKER_PATH=\\<server>\shareddata$\<path to>\Boots_Tracker_New_WIP.xlsx
M2F_DATA_DIR=C:\SDIIntelligence\m2f

Use a UNC path, not a mapped drive letter: the Windows service doesn't see mapped drives. Without M2F_TRACKER_PATH, a tracker can be loaded from Settings and data. Without M2F_DATA_DIR, the store goes in m2f_data next to app.py.

Deploying (laptop or server)

  1. Copy m2f_routes.py and the m2f folder next to app.py.
  2. Make sure app.py has the router lines, after the HR router: 
    from m2f_routes import router as m2f_router
app.include_router(m2f_router)
  3. Allow the write methods in the CORS settings in app.py (same-origin pages don't need it, but other origins listed in SDI_ALLOWED_ORIGINS do): allow_methods=["GET", "POST", "PUT", "PATCH"].
  4. Add the two .env lines above, then restart the service. No new Python packages are needed beyond the existing openpyxl.
  5. Open http://sdi-intelligence.sdi.local:8071/m2f on the server, or http://localhost:8071/m2f on a laptop.
  6. Check Settings and data: the tracker should show as loaded, and the reconciliation table should say "matches" on the formula months.

Tests

cd sdi-intelligence-backend
python -m pytest tests -q
set M2F_TRACKER=K:\...\Boots_Tracker_New_WIP.xlsx  (optional: also reconcile the real tracker)

The tests build a made-up tracker with the same layout as the real one, so no client data is stored in the repository.
