Engine Pipeline

The engine runs as a linear pipeline. Each stage hands its output to the next. Understanding the order matters — a fix in an early stage can be overwritten by a later one.

1
File discovery
main.py walks the job folder, finds PDFs and DXFs, groups them into a job structure.
2
Drawing scan + extraction
file_scan.py reads each drawing — extracts part descriptions, dimensions, materials, thicknesses. Calls extractor_patterns.py for regex/pattern matching and json_normaliser.py to normalise output.
3
DXF geometry
file_scan.py parses DXF flat patterns — measures cut perimeter, area, fold lines, hole counts using ezdxf.
4
Job merge
drawing_job_merge.py binds child parts to parent assemblies, resolves geometry inheritance, applies fallback logic for parts with no DXF.
5
Learning injection (pre_scan)
learning_engine.py checks AIEstimating.PartKnowledge — injects known-correct values at confidence ≥ 0.8 before pricing.
6
Pricing
estimator.py calculates material cost (via pricing_service.py — the 6-tier RAG chain) and labour cost (geometry × rate card). Applies credibility scoring, assembly guards, suppression logic.
7
Output generation
xlsx_output.py writes the five-sheet workbook. estimation_report.py adds the AI Provenance sheet. job_decision_report.py adds the Decision Report sheet.
8
Learning post-scan
learning_engine.py scans output for anomaly patterns, logs to AIEstimating.Corrections.

Python Modules — What Each File Does

Core engine

main.py
Entry point and orchestrator. Parses command-line arguments, walks the job folder, coordinates the full pipeline from file discovery through to output generation. Handles UTF-8 encoding for Windows console, manages the scan log, and routes errors without crashing the run.
Run with: python -u main.py --search-root "<folder>" --folder-as-job
file_scan.py
Drawing reader and part extractor. The most complex module. Reads PDFs (via pdfplumber or pypdf) and DXF files, extracts part descriptions, quantities, materials, thicknesses and dimensions. Applies the DXF-filename material override logic, calls json_normaliser.py to normalise output, and runs augment_summary_with_dxf to attach flat-pattern geometry to parts.
Note: normalise_json(summary) runs at line ~1600 — after all per-part overrides. Any material fix must be in json_normaliser.py to survive this call.
estimator.py
The cost engine. Takes the normalised job JSON and calculates material and labour cost for every part. Manages the assembly/child hierarchy, applies weldment guards, calculates credibility scores, runs the suppression check, and produces the final estimate summary. Calls pricing_service.py for every material price lookup.
pricing_service.py
The RAG price chain. Executes the 6-tier lookup for every part — UDEF → PMA_TBL → bought_in_parts (dead) → vCurrentBoughtIn → historical_quote_material_line (Jaccard RAG) → supplier catalogue URLs → web/AI fallback. Tags every price with source, supplier, confidence and price date. Returns a structured price result with full provenance.
json_normaliser.py
Material and operation normaliser. Defines normalise_material_for_part() — the authoritative function that determines each part's final material. Also normalises operation names, thicknesses and geometry values to canonical forms. This runs last in the scan pipeline — any material fix belongs here, not in file_scan.py.
drawing_job_merge.py
Assembly tree builder. Binds child parts to parent assemblies (-WA, -SA suffixes). Handles geometry fallback — if a parent has no DXF, checks if children can provide geometry. Resolves the has_children guard that preserves prior pick-best behaviour for assemblies.
extractor_patterns.py
Regex pattern library. Contains all regular expressions for extracting dimensions, materials, part numbers, thicknesses and quantities from PDF text. Centralised here so pattern changes affect all extraction without touching the main scan logic.
operation_normaliser.py
Operation name mapper. Translates between the three operation name vocabularies: AI names (e.g. laser_cutting), SDI workbook codes (e.g. LASM), and historical free-text (e.g. "Laser (Metal)"). Used by both the estimator and corpus ingest to ensure consistent operation matching.

Output generation

xlsx_output.py
Workbook writer. Generates the Estimate, Labour and Material Price Break sheets. Applies SDI formatting, formula cells, the suppression banner logic, and the cost ladder. The three-sheet base that the provenance and decision report modules extend.
estimation_report.py
AI Provenance sheet. Adds sheet 5 to the workbook — 14 columns covering part number, description, quantity, material, material source, confidence, thickness, thickness source, geometry source, cut length, operations, unit cost, extended cost, and Rate/source. The full audit trail.
estimate_full_parity_report.py / estimate_parity_pretty_report.py
Parity reports. Compare engine output against a reference manual estimate. Calculates variance per line and headline. Used for the formal parity runs (Vue Cinemas, Boots UK, ongoing benchmarks).

Data ingestion

corpus_ingest.py
Historical spreadsheet ingester. Reads SDI's historical estimate workbooks (xls/xlsx), normalises them to a JSONL comparables corpus — one job record and one part record per detail part. Feeds dbo.historical_quote_material_line (the Tier 4 RAG layer). Run against the full historical-estimates share to maximise RAG coverage.
Run with: python corpus_ingest.py --glob "K:\Estimating\**\*.xls*"
tim_rate_card_ingest.py / tim_standard_materials_ingest.py / tim_assembly_labour_ingest.py
Rate card and materials ingestion. Reads Tim's rate card workbooks and standard materials lists, normalises them to the AIEstimating.LabourRateCard and AIEstimating.JobBoughtInMaterials staging tables, ready for promotion to the live dbo tables.

Portal and services

app.py
FastAPI backend. Serves the portal HTML at /, provides the file browse and download API (/api/files, /api/file), DB health endpoint (/api/db/ping), and the BrightHR → InVentry HR pipeline routes. Every request validated by X-SDI-Key header. Path traversal prevention on all file endpoints.
Running at: http://10.0.16.151:8071
config.py
Configuration loader. Reads .env, validates required values at startup, exposes typed attributes. Fails loudly on missing config rather than running with defaults. Single source of truth for all service configuration.
tech_radar.py
AI Tech Radar. Uses Claude Opus 4.8 with web search to scan the live AI marketplace. Assesses new LLMs, libraries and tools against SDI's specific use cases (vision extraction, geometry, estimating, ERP, 3D/generative design). Tags each as ADOPT / TRIAL / ASSESS / HOLD. Writes a dated HTML report to the reports folder, browsable from the portal under Status Reports.
Run with: python tech_radar.py or python tech_radar.py --full for all 10 areas

LLM Integration — Claude in the Engine

The engine uses Claude (via the Anthropic API) in two specific, bounded roles. The cost calculation itself is entirely deterministic — Claude is never in the pricing loop.

Role 1 — Drawing extraction (vision)
When PDFs are ambiguous or non-standard, the engine can call Claude with vision capability to extract part descriptions, material callouts, dimensions and finish specifications from drawing images. This handles layouts that defeat the regex/pattern extractor — unusual title block formats, hand-annotated drawings, non-SolidWorks sources. Model: Claude Sonnet (cost-efficient for extraction volume).
Role 2 — Pricing fallback (Tier 6)
When all six database tiers miss (no price book match, no RAG match, no catalogue URL), the engine can call Claude with web search enabled to look up a current market price for an unknown bought-in component. This is a last resort — flagged in the AI Provenance sheet as "⚠ Web/AI fallback — verify" and never treated as high confidence. Disabled by default; enabled per job via config flag.
Role 3 — AI Tech Radar (tech_radar.py)
Autonomous market scanning. Claude Opus 4.8 with web search scans the AI landscape across 10 categories (LLMs, OCR, geometry, vision, ERP AI, 3D/generative, simulation, robotics, manufacturing AI, cloud infrastructure). Assesses each finding against SDI's actual capabilities and needs. Produces a dated HTML report with ADOPT / TRIAL / ASSESS / HOLD ratings. Model: Claude Opus 4.8 — the most capable model for broad multi-domain assessment.
Architecture principle: Claude handles language and ambiguity. The deterministic rules engine handles maths. Keeping these separate means the estimate is always auditable — every number traces to a rate card entry, a geometry measurement, or a price book row. Never to "the AI said so".
