A. Publish it through App Proxy

The App Proxy connector is already installed on the server and serves SDI Intelligence; SameDay uses the same one. Nothing opens on the firewall: the connector only connects out.

A1. Create the app

Entra Identity → Applications → Enterprise applications → New application → Add an on-premises application:

NameSDI SameDay Intelligence

External URLtype sdisameday; the rest is fixed, giving https://sdisameday-sdidisplays.msappproxy.net/
Pre-authenticationMicrosoft Entra ID
Connector groupDefault
Backend application timeoutLong (under Additional settings). A render or a GA can take minutes; the default cuts it off at 85 seconds.

Create, then copy two things from the app's Overview: the external URL and the Application ID. Send both to Claude.

A2. Let anyone at SDI in

Entra Same app → Properties → Assignment required? = No → Save.

Anyone with an SDI Microsoft account can then open it, and nobody else can reach it at all. There is nobody to assign, so the step that once stopped Kayleigh (AADSTS50105) does not exist for this app.

A3. Hand SameDay the person's name

A4. MFA

Entra If your Conditional Access MFA policy names its apps (for example MFA — SDI Intelligence), add SDI SameDay Intelligence to its target resources. If MFA covers all apps already, there is nothing to do.

B. Tell SameDay to trust the connector

Server Remote Desktop, PowerShell opened with Run as administrator:

$f = "C:\SDI_Automation\.env"
$keep = Get-Content $f | Where-Object { $_ -notmatch '^\s*LITE_TRUST_FROM\s*=' }
[IO.File]::WriteAllLines($f, [string[]]($keep + "LITE_TRUST_FROM=10.0.0.5,127.0.0.1"))
Restart-Service SDISameDay

It prints nothing, and it never shows the keys in the same file. The connector runs on this server, so it arrives at SameDay from 10.0.0.5: SameDay now believes the name in the headers only when they come from there. Someone in the office typing http://10.0.0.5:5020 comes from their own address and still gets the team code, so nobody can pretend to be somebody else.

Change it to secure=request.is_secure, on K: and on the laptop. E. Updating SameDay on the server

Since 4 November SameDay's code is in its own private repository, github.com/jbgray1874/sdi-sameday. The "any order" and noisy-room changes are there, and so is the cookie fix above. Updates go from the repository to the server. Laptop once, to copy the script across:

Copy-Item C:\ClaudeVision\sdi-intelligence-backend\deploy\Update-SameDay.ps1 \\10.0.0.5\c$\Tools\

Server as administrator. To try the new changes before they go onto main:

powershell -ExecutionPolicy Bypass -File C:\Tools\Update-SameDay.ps1 -Branch claude/inspiring-planck-8juriz

Without -Branch it takes main. It keeps the code it replaces in C:\SDI_Automation\backups\ and never touches the keys, chats, uploads or spend log. It finishes only when SameDay reports the new version, and it says how to put the old code back.

Not UPDATE_SAME_DAY.bat on the server. Muhammad's batch file copies K: (the older code, without the cookie fix) and then starts a second SameDay outside its Windows service, and that copy fights the service for port 5020. It is still right for Muhammad's own laptop.

Muhammad's changes on K: still reach the repository. Publish-SameDay-Code.ps1 puts each copy of K: on its own branch (from-k) and merges only what changed on K: since the last copy, so it never undoes work made in the repository. If both changed the same lines, it stops and names the files.
