🏗 SolidWorks COM API — The Primary Data Source for SDI-Originated Jobs SolidWorks is licensed ✓ — build this first
win32com£0 per callGround-truth geometry Eliminates PDF-geometry pipelineDirect ingestion — no file-hunting

Since SolidWorks is already licensed on the estimating machine, the COM API is the primary data path for all SDI-originated drawings — not a future option. This single decision eliminates the entire PDF-geometry extraction problem class (the BENDLINES inflation bug, the 2621-01C 1.77× calibration error, the credibility gate firing) because you are reading from the model rather than reconstructing it from a drawing export.

What the API returns, per part:
win32com.client.Dispatch("SldWorks.Application") then open the .sldprt file — from it you can read directly:

  • Flat-pattern dimensions: SW-Bounding Box Length, SW-Bounding Box Width — the exact laser-cut sheet size with no extraction noise
  • Cut perimeter: flat-pattern boundary via Sheet Metal feature — actual cut path, not vector-path sum
  • Bend count and bend allowance: SW-Number of Bends, SW-Bend Allowance — the values the press-brake operator actually works to
  • Material and thickness: SW-Material, SW-Sheet Metal Thickness — the designer's intent, not a text scan
  • Weight: SW-Mass — feeds material cost calculation directly
  • Custom properties: Description, Finish, Supplier, Revision — whatever fields the Design team have populated
  • Hole count and sizes: from sheet metal feature punch lists or hole wizard features
From the .sldasm assembly file:
  • BOM table: IFeatureManager → GetTableAnnotations gives part number, description, quantity per assembly — exact values, no regex, no text-dump ambiguity
  • Assembly tree quantities: sub-assembly multipliers (the bom_tree 1→2 ×2 problem) are already resolved in the SW BOM — FIXING125 comes back as 4 automatically because SW counted it at the assembly level
  • Weldment cut list: for structural members (tubes, sections like 3886-01) — LENGTH, QTY, MATERIAL, PROFILE from the weldment cut list property. This directly replaces the tube catalogue-lookup guessing — you get the exact section type, length, and quantity as designed
From the .slddrw drawing file:
  • Notes and annotations: the assembly notes on page 10 ("FIXING5 4.0×10mm DOME RIVET 2... JUNCTION BOX...") are structured note objects in SW, not free text in a PDF. They can be read as strings via the drawing API — cleaner source for the note-scan finder than pdfplumber
  • Title block fields: MATERIAL, REVISION, DATE, DESCRIPTION — as structured data, not text dump to regex
  • Scale: the calibration problem (page 9's 1.77× mystery) doesn't exist when you read the actual drawing scale property
Direct ingestion — no file hunting: the COM API opens files by path. Point it at the SolidWorks project folder, enumerate all .sldasm files, open each, extract. No folder scanning, no PDF-to-text extraction, no DXF matching. The engine's drawing_job_merge.py file-scan step becomes a SW project folder walk instead. The "stray-space filename" bug (_revA .dxf) and the three-1450-file ambiguity disappear because SW part numbers are unambiguous model identifiers.

Cost: £0 per call. The licence is already paid. Running cost is local compute: COM API calls take 1–5 seconds per part to open and extract. A 15-part job takes under 2 minutes total, running in the background while the designer is doing something else.

Integration pattern: The Python call shape is identical to what the engine already does with pyodbc (open connection, query, close). Replace pyodbc.connect(...) with win32com.client.Dispatch("SldWorks.Application"). The rest of the estimating pipeline (pricing, credibility gate, workbook population) is untouched.

→ Build this first. One Python module (~200 lines), replaces geometry_features.py for all SDI-originated drawings. No infrastructure change needed — SW is already running on the machine.

Drawing Resolution — What Resolution Actually Helps 300–600 DPI is the window · "24K" is a misconception
300 DPI → BOM text, title blocks 600 DPI → fine dimension lines Beyond 600 DPI → no gain, slower

The term "24K" comes from video resolution (approx 24,000 pixels wide). Applied to an A1 engineering drawing this would mean rendering at approximately 17,000 DPI — completely counterproductive. Vision LLMs (Gemini, Claude, GPT) all resize images internally to fit their tile-processing architecture (typically 1024–2048 pixels per tile) regardless of input resolution. Sending a 24K image doesn't make the model see more detail — it sees the same downsampled version but you've paid for a much larger file upload and processing time.

The practical window for engineering drawings:

  • 150 DPI — readable large text, usable for GA/assembly page overview and BOM table identification. Too low for dimension callout text (typically 8–10pt on a drawing).
  • 300 DPI — optimal for BOM text extraction, title block reading, note-scan (what the note-scanner currently needs). Standard for OCR. This is the target for most pages.
  • 600 DPI — better for fine dimension lines on detailed mechanical drawings (the 4.5mm/59.0mm hole callouts on 1455-C-001 page 12), closely-spaced peg-hole grids (1449-01C), and small annotation text. Worth using for detail pages; overkill for assembly/GA pages.
  • Beyond 600 DPI — no accuracy gain for vision LLMs, files 4× larger, upload time increases, no benefit. Tested by multiple independent evaluations: 300→600 DPI helps; 600→1200 DPI does not.
Practical implementation: use pymupdf's page.get_pixmap(dpi=300) for assembly/GA pages and dpi=600 for detail pages with fine geometry. The page-role classifier the engine already runs (assembly vs detail) naturally provides this split — no new classification needed.

For DXF files: DXF is a vector format — resolution only affects the rasterised output quality, not the underlying geometry data. Since the SolidWorks COM API gives you the actual vector geometry directly (no rasterisation step), resolution is irrelevant for SW-originated parts. For external DXFs (old Milwaukee/TTI files), render at 300 DPI which is more than adequate for all SDI drawing formats.

Bottom line: the accuracy gains come from using a vision LLM on a well-prepared 300/600 DPI image, not from raw pixel count. A Gemini 3.5 Flash call on a 300 DPI A3 page will extract BOM data far more accurately than the current geometry_features.py at any resolution, because Gemini reads the drawn callouts rather than counting vector paths.

The engine currently uses only the exported DXF and PDF. From the same SolidWorks project, the COM API can extract much richer data from five distinct file types:

.sldprt (Sheet Metal Parts) — the most important for estimating: SW-Bounding Box Length/Width = flat-pattern dimensions; SW-Number of Bends = bend count; SW-Sheet Metal Thickness = material gauge; SW-Material = exact material; SW-Mass = weight for material cost. Cut perimeter via sheet metal flat-pattern feature. Hole wizard holes: count, diameter, and type (through, tapped, counterbore) — directly feeds the pierce count the engine currently estimates from circle-entity counts.

.sldasm (Assemblies): The BOM table extracted via InsertBomTable4 / GetTableAnnotations gives the definitive part-number, description, and quantity-per-assembly for every component — fabricated parts AND bought-in items (fixings, vinyl, looms, junction boxes) if the designer has added them. This is the structural fix for the FIXING125 ×2 vs ×4 ambiguity: SW BOM already shows qty 4 because it counts at bay level.

.slddrw (Drawings): Notes and annotations (the assembly notes the note-scanner currently reads from PDF text) are structured objects in the drawing API — read as strings, cleaner than pdfplumber. Title block fields (material, revision, date, description, surface finish) are named custom properties, not text to regex. Scale is a drawing-level property — eliminates the calibration step.

Weldment cut lists (.sldprt or .sldasm): for structural tube members (like 3886-01's "30×60×1.50mm TUBE 1125mm"), the weldment cut list property carries LENGTH, QTY, MATERIAL, and PROFILE. The engine currently reads "30 x 60 x 1.50mm TUBE" from a PDF page in OCR. The COM API returns this as structured data, correctly split into section size, wall thickness, and cut length. Direct feed into the tube catalogue lookup — no regex needed.

Design tables (Excel-driven configurations): if SDI uses SW design tables for standard bay widths (500mm, 750mm, 1000mm configurations), the COM API can read which configuration is active and extract its specific parameters. Useful for range pricing: run the API across all configurations at once.

Custom properties: any designer-entered data — standard finish (RAL3020 Traffic Red), supplier, approved-material-list reference, drawing number — all readable as named properties. Can auto-populate the estimating sheet's metadata fields without anyone typing them.

eDrawings (.eprt, .easm, .edrw): lightweight exports that don't require a full SolidWorks licence on the viewer machine. If estimating ever needs to run on a machine without SW installed, eDrawings COM can read basic geometry and BOM data. Lower fidelity than full SW COM — no cut-list properties, no weldment data.

Where rasterisation (PDF → image) is needed in the pipeline — and where it is not:

Rasterisation is only needed inside vision_extractor.py — the Gemini path for PDF-only external drawings. Every other part of the pipeline works on vector data and does not need it:
