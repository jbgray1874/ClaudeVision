3Labour — every Rate Per Hour explained

The engine writes four cells per row: operation, description, quantity, and the Rate Per Hour (pieces/hour). Everything else — department, £/hr, setup, hours, value — is computed by SDI's own template. So the Rate Per Hour is the only number the engine decides, and it is the one to scrutinise. Below, each row states exactly how that number was arrived at.

There are only four ways to know a throughput, and each row uses the right one

Formula the template computes it from geometry — we read it.
Derived the drawing carries the driver — we compute it in Python.
Banded only part size drives it — we use the median of past jobs of that size.
Estimator only Tim knows it — we cannot derive it, and we flag it.

Laser (Metal) 311.13000.45 Formula The template's own Laser Rate Calculator takes the cutting speed for 2mm (75 mm/s), the blank perimeter, 2 holes and the internal cut distance and returns 3600 ÷ 11.6 sec = 311/hr. The engine writes a formula pointing at that cell, so it tracks any change you make to your cutting speeds. Within 4% of Tim.
Fold 93.8900.84 Derived There is no fold calculator in the template — Tim judges it. The engine derives it from the bend count read out of the DXF (2 bends), plus a per-bend handling time. Within 4% of Tim, with no calculator to read — the geometry alone was enough.
Robomac 7093,0000.20 Substituted → to be Derived Currently a flat default. It should be derived from wire length and bend count, exactly like Fold — the driver is in the geometry. Tim books 3,000/hr to cut this straight 65mm stud and 100/hr to form a 975mm wire frame on 7670: same operation, 30× apart, because it is about the wire, not an average. On this job the cost impact is 3p, so it is low priority, but the method is wrong and will be fixed.
P.Coat 4589572.55 Banded by size No formula can compute how many parts hang on a bar — it depends on the part. We use the median of past jobs of the same size. 1310 is a small part, and small parts hang more per bar, so they coat faster: our size band measures 638/hr for parts this size against the blended 458 we shipped. Wiring that in takes £2.55 → £2.33. The rest of the gap to Tim's £2.00 is the rate — see the two-rate-cards note.
Assemble/pack 581200.64 Banded by size Same as P.Coat — there is nothing in the geometry that says how long a part takes to bag and box, so we use the median of past jobs of that size. Our size band measures 90/hr for small parts against the blended 58. £0.64 → £0.46. The residual to Tim's £0.29 is setup: our template books 15 min, Tim's books 5 — the template-version issue, not the throughput.
Weld (CO2) 29501.86 Estimator only Weld time depends on the number of welds, which appears on no drawing. It cannot be derived from geometry and it is not a function of part size — the size band for weld is noise (20 / 12 / 7.5 / 15 across the bands). The engine uses a placeholder default and flags it. This is the single largest gap on the job (£0.61) and it needs a rule from Tim — see the questions.

What this table is really showing

The two rows the engine reads (Laser, Fold) are within 4%. The four it substitutes are all wrong, and all in the same direction. Two of those four (Pack, P.Coat) we can fix from your own history today. One (Robomac) we will fix by deriving it. And one (Weld) we cannot fix at all without a rule from Tim, because the information is on no drawing.

The goal is that no row on this table is ever a "substituted" number. Every one should be read from the template, derived from the drawing, banded from measured history, or — where only the estimator knows — visibly carrying the estimator's own figure with a flag saying so.
