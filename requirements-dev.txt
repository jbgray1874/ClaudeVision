# Test-only dependencies. Deliberately NOT in requirements.txt: the service and the
# runner do not need them, and the estimating venv on a production machine should
# carry what it runs, not what verifies it.
#
#   .\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
#
# pytest-randomly shuffles the order every run. It is here because 90 tests once
# passed in one order and failed in another, through state one of them left behind
# in sys.modules — a suite that only passes in collection order has not been run.
pytest>=8.0
pytest-randomly>=4.0

# fastapi's TestClient needs httpx, and WITHOUT IT EVERY ROUTE TEST SKIPS. Fifteen of them did,
# for long enough that one was still asserting a refusal the code had deliberately stopped
# making — a test file for a guard that no longer existed, green because `importorskip` had
# quietly turned the whole module off. A skip is not a pass, and a suite that reports 24 of them
# is not saying so loudly enough to notice.
httpx>=0.27

# ── AND THE SERVICE'S OWN MANIFEST, OR HALF THE SUITE DOES NOT RUN ───────────
# These dev dependencies alone are not enough. voicecrm, auth and the route
# tests import httpx, msal, itsdangerous and openpyxl, which are declared in
# sdi-intelligence-backend/requirements.txt - and WITHOUT THEM those modules
# fail to import and unittest reports them as errors rather than failures. On
# 30 October that was 26 modules and about 500 tests, quietly not running,
# while the remaining 435 reported "OK". The same trap as the skips above, one
# level up: an error at import is not a failing test, and a suite that cannot
# load half of itself is not saying so loudly enough.
#
#   python -m pip install -r requirements-dev.txt
#   python -m pip install -r sdi-intelligence-backend/requirements.txt
#
# Then the whole suite runs: 936 tests and ~1,550 subtests.
