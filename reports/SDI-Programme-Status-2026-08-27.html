What the one axis shows that three trackers did not

Three go-lives inside five weeks. Drawing Search on 25 Sep, Technical Design P1 on 15 Sep and P2 on 24 Sep, and the estimating engine targeting September / October. Four releases into the same business, from three owners who do not share a plan, inside the same month — and two of them land on consecutive days.

Nothing blocks anything. That is the good news and it is worth stating plainly: no workstream waits on another, so a slip in one does not move the others. The exposure is not dependency, it is attention — the same estimators and designers are the users for more than one of these.

Deterministic cost-estimating engine — SolidWorks PDF and DXF drawings in, a costed five-tab workbook out, mirroring the manual estimating workbook to the cell. In parallel run with Tim, Howard and Tony.

Faults where the system said it had worked when it had not

Each of these had already cost real time before it was found. All are fixed.

A run that produces no workbook now says soFixed

A job ran for sixteen minutes, reported done, and produced nothing. The cause was a single missing template file — but every deliverable hangs off the workbook, so one missing file silently took out the estimate, the quote, the job report, the Decision Report and the AI Provenance sheet at once, while the runner still reported success.

The run now fails with an explanation, and the template is checked before the run starts rather than at the point it is needed.

What you'll notice: a failed run says why it failed, at the start, instead of sixteen minutes later saying nothing at all.

The parity report now shows what it actually comparedFixed

The comparison against a manual estimate had several faults at once. The HTML report was not always written — you would get the JSON and CSV and nothing readable. Where it was written, the variance column was calculated from a different pair of numbers than the difference column beside it, so the two disagreed. Unmatched items, flagged parts and unpriced rows were either missing or rendered blank.

The report is now written on every run, and every figure in it comes from the same source as the figure next to it.

What you'll notice: three files per comparison, not two — and the HTML one is the one to read.

Uploaded workbooks keep their own nameFixed

A manual estimate dropped into the comparison was renamed on the way in, so the report referred to a file you did not recognise. It keeps its name now.

The print pack stopped crying wolfFixed

The cover sheet listed drawings as missing when they were already printed further down the pack, and counted internal working files as drawings. Both corrected.

Health reported more honestlyFixed

The health check reports whether the estimating template is reachable and marks itself degraded when it is not, rather than looking healthy until a run fails.

Comparison files download as CSVFixed

Previously returned an error.

Pricing — where a number comes from, and what it is worth

The price chain, stated as it is wiredDocumented

Seven sources, strictly ordered, first hit wins — there is no scoring across sources. In order: UDEF parts master (exact code 0.95, fuzzy 0.82) → ERP parts master (PMA, purchased items, 0.55–0.88) → bought-in catalogue (0.93 / 0.80) → historical RAG over past quote lines (0.75 + match, less staleness) → supplier catalogue (0.65) → standard commodity (0.50) → web / LLM (capped 0.68).

The first six are reproducible; the seventh is not, which is why it is last and capped. A zero is never a price at any step — every source refuses a row costed at £0.00 rather than passing it on as a bargain.

A category word was being used as a part codeFixed

Brought by Tim, which is the best kind of bug report. He can find FIXING41, FIXING513 and FIXING1122 in the parts master. He cannot find FIXING — because FIXING is the word for what the thing IS, not an identifier, and SDI never minted one for those lines. Their identity is entirely in the description.

The engine was asking the catalogue for FIXING as though it were a code. In UDEF that produced no wrong price — the catch-all row there is £0.00 — but it blinded the description arm of the same query, so those lines came back empty whether or not their description matched anything. Around 900 MISC rows did the same to every line coded MISC. In the ERP parts master it was worse: that query filters on cost > 0, so a priced catch-all would have been returned at the highest confidence the chain can express, pricing a socket cap screw, a button head and an aluminium rivet identically.

Class words are now refused as identifiers everywhere, and the line falls to description matching instead — where M6x16.0mm SOCKET CAP SCREW, BZP is a far better key than FIXING ever was.

Still open, and recorded as a failing test rather than hidden: the description scorer counts words and has no idea which one is the size. A wrong-size line of the same family scores 0.71; the right part written with different punctuation scores 0.50 — and the higher score wins. For a screw that is pennies. The mechanism is not about pennies, and size-aware matching is its own piece of work.

Supplier price lists can be loaded as catalogue rowsNew

An ingester that turns a supplier's spreadsheet into catalogue rows on a fixed shape — supplier, their SKU, our SKU, description, class, unit, thickness, sheet size, net price, valid-from, source file. It reads the unit from the column, then the price heading, then the description, and says which of the three it used, because guessing /m² where the sheet meant /sheet is a three-fold error on a 2500×1250 panel.

It refuses a file that is not a price list rather than half-parsing one, and quotes back the header row it read so a refusal can be argued with. Elite, Eagle and Thermaset are the first three lists to load.

Database credentials moved out of the source treeFixed

The SDILive password was a literal in seventeen tracked files and the .env holding the live values was itself tracked by git — so "put the new password in .env only" would have committed it straight back into the same exposure. Both are corrected: the password is read from the environment, the environment files are untracked and ignored, and a template lists every setting without any of the values.

Rotation done on the laptop, verified against the live catalogue. Still to do on SDI-APP01 — see Known and open.

What it is, in one paragraph

Two threads under one workstream. First, the Document Manager tools — they read SolidWorks project data without needing a SolidWorks seat, and pull the right drawing pack for a job straight into the estimating app and into the shop-floor Production folder. Then an SDI in-house PDM, built in four phases, giving engineering proper file management, revision control and release workflows.

This is not integration with the SOLIDWORKS PDM vault. SDI is building its own PDM alongside, and the Document Manager tools read the live CAD share read-only — they never write to it. Getting that wrong changes what the work is, so it is stated explicitly.

Built on GitLab and LFS with a Document Manager intelligence layer over PostgreSQL. Around 50 requirements captured from design, engineering and directors; that register is still open.

Why it runs into January, and it is not the amount of work

There is one developer. Requirement collection, development, unit testing, peer review, deployment and go-live are all hands-on and have to run one at a time — only user testing overlaps, because users do that. Add leave from 10 December to 4 January and the last two PDM phases land in the new year.

The dates are a capacity constraint, not an estimate of effort. If these need to come forward, the lever is a second pair of hands, not a tighter plan.

Four finished tools were waiting on a SolidWorks licence — the seat is now installedChanged

These were never planned work. They are built, demoed to Ed Cooper and Ian B, and every one carried go-live subject to SolidWorks licence. A permanent seat is now installed on the estimating laptop, so the constraint is lifted there. The remaining question is which machines get a seat, not whether the tools can run.

  • C1 · Multi-format export pack — one click from a finished design to DXF flat patterns, PDF and DWG drawings, STEP per part and IGES per body, laid out to mirror the project folder.
  • C2 · Design validation suite — topple, weight, interference and cross-part hole alignment, all in one pass and one report. Topple checked against a live assembly at roughly 25.9°.
  • C3 · Drawing generation — views, sheets, BOM and title block created automatically from a finished model; designers add the critical dimensions.
  • C4 · Machine tolerance checks — a design measured against the real TRUMPF tool list and SDI standards. Still in proof of concept.

Why C1 matters most. The estimating engine's single largest source of inaccuracy is drawings arriving without flat patterns — with no DXF the engine has to infer geometry, and that is where the wrong numbers come from. C1 generates those flat patterns, and it works today.

Three overlaps worth knowing about before they bite

What it actually does, since the name does not say

Image and drawing search for the design studio. CLIP-based visual search with PDF indexing over roughly 268,000 images, GPU-accelerated with a CPU fallback, behind a Flask UI with a scan cache. SDI has drawn the same bracket, the same shelf and the same plinth many times over, and until now the only index of that was what a designer happened to remember.

It is not the estimating engine's description matching pointed at a different table. That scores word overlap between two pieces of text; this searches the images, which is why it can find a fixture whose description never said what it looked like. The two may meet later — a drawing found here carries a part code, and a part code is a key the price chain already understands — but they are separate pieces of work today.

How this differs from SDI Brief & Concept Intelligence

They sit next to each other on the service list and the difference is worth stating. Brief & Concept takes a brief and generates something new — renders, concepts, parametric 3D. Client Briefing takes the same brief and finds what already exists: the fixtures SDI has already built for that requirement, and the jobs they came from. They share brief capture and diverge there. A client asking for something SDI has built before should be shown it, not sold a concept render of it.

The service list had grown up piecemeal — some entries began with "AI", some did not, and nothing said they belonged to SDI. They now share one convention.

SDI Estimating Intelligence, SDI Technical Design Intelligence, SDI Drawing Search Intelligence, SDI Client Briefing Intelligence, SDI Production Scheduling Intelligence, SDI Quality Inspection Intelligence, and so on through the list.

Two deliberate exceptions. The six co-worker agents keep the word Agent — they act on their own rather than being a capability you invoke, and the distinction is worth keeping. The sidebar and the portal now agreeFixed

Three copies of one service list, and two had stopped agreeing with the third. The portal builds its navigation from a single array; the estimating page and the guide each carry a hand-copied sidebar written when there was one list and nobody had renamed anything. So the estimating page went on offering "Estimating" and "AI Voice Agents" while the portal one click away called the same things something else — and neither copy had an entry for the second workstream of the whole programme.

The duplication is deliberate — sharing one list means a template layer or a network call in front of the sidebar, for a list that changes twice a year. A test now pins the copies to the portal, so drift fails the build instead of reaching a screen.

07 Where things run

Two portals, and only one of them can produce an estimate. This is the most common source of confusion, so it is worth being plain about.

Primary · estimating
http://localhost:8072

James's laptop. Has the engine and the runner attached, so this is the only host that can produce an estimate, a quote or a print pack. Now also the only machine with a permanent SolidWorks seat.

Secondary · reference
http://10.0.0.5:8071

SDI-APP01. Portal pages and comparison reports. No runner and no SOLIDWORKS seat, so it cannot run a job — the estimating screen loads but will not produce a result.

Updating the portal needs a refresh, not a restart

Portal pages are read fresh from disk on every request, so copying updated pages to the staging area is enough — there is nothing to restart. If a page looks out of date press Ctrl+F5, or in Edge use DevTools → Empty cache and hard refresh.

The exception is .env. That is read once when the service starts, so a changed setting — a rotated password, a new path — does need the service restarting.

08 Known and open

Recorded here rather than left to be rediscovered. Ordered by what it costs to leave alone.

A published API secret has never been rotatedAct

The BrightHR client secret has been in this repository's git history since its first commit in April, and the repository was public for four months. It is now private and the environment files are untracked — neither of those undoes history. Anyone who has ever cloned it still has the value.

Rotating the credential is the only cure. The SDILive database password has been rotated and verified; this one has not.

The new database password is not yet on SDI-APP01Open

The SDILive login was rotated and the laptop is running on the new one, verified against the live catalogue. The server's two environment files still carry the old value and the service needs restarting after they are updated. Worth running xp_readerrorlog for failed logins a day or two after, to find any consumer nobody remembered.

One trap worth knowing: the password is pasted into an ODBC connection string, where a semicolon ends the value and starts a new keyword. The server then answers "Login failed" — which reads as the wrong password rather than an unusable one. The engine now refuses such a password up front and names the character.

The server cannot report which build it is runningOpen

The health check shows commit: unknown on SDI-APP01 because of how that service is started, and parity runs there need one setting pointed at the right Python. A configuration script that fixes both has been written and not yet run on the server. This is the one host where two portals can drift apart, so the field exists precisely to catch it.

Three costing faults on the Dyson packOpen

  • Cross-job contamination — a fixing from an unrelated fragrance-cabinet job was costed onto a Dyson estimate. The test that was supposed to guard this was found to be vacuous and has been removed; the guard itself needs rebuilding.
  • Prose read as a part number — a draughtsman's name and date in a title block was read as a part, given a material from a revision note that said the panel had been removed, and costed anyway.
  • Powder coating at £0.00 on a powder-coated job. The rate question is settled — the live rate is £9.73/kg, evidenced from the manual sheets on jobs 1303A and 1304; a second £12.50 constant was traced and is dead code with no callers. What remains open is the policy: whether an unstated finish defaults to powder with a visible assumption flag, or is a required estimator decision.

Two price sources are wired to tables that are emptyOpen

Rung 3 of the price chain reads bought_in_parts where is_active = 1. A migration moved that catalogue to a new table and set every migrated row inactive, so the rung returns nothing — the successor holds 44 rows. And drawing_priced_estimate, where a priced estimate is meant to be saved, does not exist: no run has ever recorded which source won a price, which is why the question "do we genuinely do all these lookups?" could only be answered by reading code.

Two decisions, both small: repoint rung 3 at the successor table, and either create the results table or remove the save.

Size is not weighted in description matchingOpen

Historical price matching scores word overlap, and has no idea which word is the size. A wrong-size line of the same family can outscore the right part written with different punctuation. Recorded as a deliberately failing test so it cannot be forgotten. Fixing it changes matching for every priced line, so it wants doing on its own.

Housekeeping in the parts masterOpen

A row coded FIXING whose description is the word "Description", and roughly 900 duplicate MISC rows all reading "TRY NOT TO USE THIS PART". All are £0.00, so none of them ever mispriced a job — but they are what the engine trips over, and they are cheap to remove.

DWG drawings are silently ignoredParked

No converter is configured, so a DWG in a pack contributes nothing and says nothing. Parked deliberately, recorded so it is not rediscovered as a surprise.
